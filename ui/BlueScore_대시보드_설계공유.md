## 0. 한 줄 요약

> 대시보드를 **어업인용 / 심사역용 두 페이지로 분리**합니다. 그 과정에서 기존 발표용 목업 화면의 **상위 % 계산식 오류**를 발견해 고칩니다. 이 때문에 `score/`에 유사 선박군 **전체 점수 분포**를 요청드리고, 발표 자료의 수치 동기화가 필요합니다.

## 1. 결정 사항

### (1) 화면을 두 개로 분리

기획서 (8-2)가 어업인과 심사역의 흐름을 따로 정의하고 있으나, 발표용 목업(`blue_score_dashboard_3.html`)은 한 페이지에 섞여 있었습니다. 어업인에게 문서번호·해시·승인 버튼은 의미가 없고, 심사역에게 개선 코칭은 부차적입니다.

```
app.py              진입점 · 네비게이션만
ui/fisher.py        어업인 화면
ui/bank.py          심사역 화면
ui/api_client.py    FastAPI HTTP 전송
ui/adapter.py       API 응답을 화면 키로 변환
api/ services/      계산·설명·업무 상태의 단일 창구
```

**핵심 제약** — 두 화면의 숫자는 반드시 같은 계산에서 나와야 합니다. 현재는 FastAPI와
SQLite의 같은 `scoreRunId`를 두 화면이 조회하며, `ui/adapter.py`는 계산하지 않습니다.
두 화면의 점수가 다르면 "제3자가 관측한 동일한 점수"라는 서비스 전제가 무너집니다.

| | 어업인 화면 | 심사역 화면 |
|---|---|---|
| 공통 (동일 숫자) | 점수 · 2축 분해 · 유사군 내 위치 · 지도 | 좌동 |
| 고유 | 개선 시뮬레이터(주역) · 평이한 설명 · 예상 우대 구간 | 자격 요건 · SHAP 원수치 · 데이터 출처/신선도 · 해시 · 승인·보류 |
| 미노출 | 문서번호 · 해시 · 승인 버튼 · SHAP 원수치 | 코칭 문구 (시뮬레이터는 접힘 참고용) |

### (2) 상위 % 산출식 수정

목업의 계산식에 오류가 있었습니다. 목업은 데이터 확인 전에 발표용으로 급히 만든 화면이라 예상된 일이며, 실제 구현에서는 바로잡습니다.

```
현재 (틀림)   상위% = 0.65 × A축상위% + 0.35 × B축상위%
              → 백분위끼리 가중평균한 값. 통계적으로 성립하지 않음
              → 실제 계산 시 31%가 나오는데 화면 표기는 27%로, 값도 어긋나 있었음

올바름        ① 유사군 42척 각각의 BlueScore를 먼저 산출
              ② 그 42개 점수 분포 안에서 이 배의 순위를 매김
```

**영향 범위는 좁습니다.** `0.65 × 81 + 0.35 × 57 = 72.6` 산식과 축 점수 81/57은 그대로 유효합니다. 바뀌는 것은 **"상위 N%" 숫자뿐**입니다.

### 수정 후 실제 값 (2026-08-14 기준)

합성 분포로 계산한 결과입니다. `score/`의 실산출이 붙으면 다시 바뀝니다.

| 선박 | BlueScore | A축 (상위%) | B축 (상위%) | **종합 상위%** | 90% 구간 |
| --- | ---: | ---: | ---: | ---: | --- |
| 선박 A | 72.6 | 81 (24%) | 57 (40%) | **17%** | 7 – 26% |
| 선박 B | 56.9 | 52 (46%) | 66 (35%) | **32%** | 22 – 46% |
| 선박 C | 84.8 | 88 (10%) | 79 (16%) | **3%** | 1 – 10% |

발표에 쓰던 **"42척 중 상위 27%" → "42척 중 상위 17%"** 로 바뀝니다.

**부수적으로 발견한 것** — 선박 B와 C는 목업의 총점이 자기 산식과 어긋나 있었습니다
(B는 58.4로 표기됐으나 `0.65×52 + 0.35×66 = 56.9`, C는 85.3으로 표기됐으나 84.8).
발표에 쓰이는 선박 A(72.6)는 정확했습니다.

**90% 구간이 넓다는 점(7–26%)** 을 그대로 화면에 표기했습니다. 42척은 작은 표본이라
순위가 흔들립니다. 이걸 숨기면 "AI가 정밀한 척한다"는 지적을 받고, 드러내면 오히려
심사위원이 물어볼 질문을 화면이 먼저 답합니다.

### (3) 지도 라이브러리

**Leaflet + Esri World Imagery**를 씁니다. 처음에 pydeck(`st.pydeck_chart`)으로 만들었으나
Carto·Mapbox 모두 베이스맵이 뜨지 않고 점만 찍혔습니다. 구글 맵은 API 키에 더해 결제 등록이
필요해 팀 전원이 실행하기 어렵습니다.

그래서 발표용 목업(`blue_score_dashboard_3.html`)이 쓰던 조합을 그대로 가져왔습니다.
API 키가 필요 없고 이미 동작이 확인된 방식이며, 시연 이미지의 어두운 위성 지도와 같은
계열입니다. `st.components.v1.html`로 iframe에 띄워 다른 위젯의 재실행과 분리했습니다.

알아둘 것 두 가지:

- **줌은 파이썬에서 계산해 넘깁니다.** iframe 안에서는 지도 크기가 확정되기 전에 스크립트가
  돌아 Leaflet의 `fitBounds`가 엉뚱한 줌을 잡습니다.
- **줌 상한은 11입니다.** 더 당기면 먼바다라 위성 이미지에 아무것도 없어 화면이 검게만
  보입니다. 같은 이유로 mock 항적 좌표를 독도·울릉도 인근으로 배치했습니다.

## 2. 담당자별 요청

### 김준기 · 오동규 (`score/`)

**① 유사 선박군 전체의 점수 분포가 필요합니다.**

상위 %를 올바르게 구하려면 대상 선박 1척이 아니라 유사군 N척 전체의 BlueScore가 있어야 합니다. 현재 mock은 `peerGroup: {count, topPercent}` 스칼라 두 개뿐이라 분포가 없습니다.

산출 함수가 다음을 반환하도록 요청드립니다.

```
peerGroup: {
  count: 42,
  scores: [ 41.2, 44.8, ... ],   ← 유사군 전체 BlueScore 배열 (본 선박 포함)
  selfIndex: 17                  ← 배열 내 본 선박 위치
}
```

이게 있으면 상위 %가 정확해지고, 화면의 유사군 분포 그래프도 실제 데이터로 그릴 수 있습니다. (현재 목업은 난수로 점을 뿌리고 있어 리렌더할 때마다 분포가 바뀝니다.)

**② 시뮬레이터의 축 간 트레이드오프 계수가 필요합니다.**

`BlueScore_점수산정_요약.md`에 *"멀리 옮기면 연료를 더 써서 B축이 깎인다"* 고 명시돼 있는데, 목업의 시뮬레이터는 A축과 B축을 독립적으로 올립니다. 두 슬라이더를 모두 최대로 밀면 물리적으로 불가능한 조합이 나오는데도 점수가 올라갑니다. **데모 중 누가 슬라이더를 끝까지 밀면 그 자리에서 드러납니다.**

A축 개선이 B축에 주는 반작용을 계수로 주시면 화면에 "이 조합은 연료 +4% 대가가 따릅니다"로 표시하겠습니다.

**③ (가능하면) 점수의 불확실성 구간**

기획서 9번이 "점수는 추정치로 표기한다"고 정해뒀는데 목업에는 `72.6 / 100`만 있습니다. 42척 표본에서 나온 값에는 오차가 있고, 이를 숨기면 "AI가 정밀한 척한다"는 지적을 받습니다. 부트스트랩 신뢰구간이면 계산 부담도 적습니다. 화면에는 `72.6 ± 3.2`로 표기할 계획입니다. 우선순위는 ①②보다 낮습니다.

### 김준기 · 오동규 (`chain/`)

목업의 해시(`simpleHash`)는 **SHA-256이 아니라 화면 시연용 자체 함수**입니다. `CLAUDE.md` 확정 규칙 5번(`sort_keys=True`, 소수점 둘째 자리 반올림 후 문자열화, 빈 값은 키 자체 제외)을 따르지 않습니다.

화면에서는 `chain/`의 실제 해시 생성 함수를 호출할 예정이니, 함수 시그니처가 정해지면 알려주세요. 그 전까지는 "해시 생성 대기" 상태로 표시해 두겠습니다.

### 김태윤 (`data/`)

**⓪ [확인 요청] 실제 매칭된 샘플 3척이 전부 원양어선입니다**

2026-08-14에 올려주신 `data/mock/sample_vessels.json`을 보니 매칭 확정
(`confirmed_fishing`) 3척이 모두 이렇습니다.

| 선박명 | 총톤수 | 어업종 | 이벤트 위치 |
| --- | ---: | --- | --- |
| NO101 OYANG | 400 t | `92[원양 어선]` | 남위 46°, 서경 60° (남대서양) |
| UDARNYI | 729 t | `92[원양 어선]` | 〃 인근 |
| NO.99 OYANG | 2,187 t | `92[원양 어선]` | 〃 인근 |

그런데 기획서는 **1차 범위를 근해어선으로 한정**하고 있고, 소형 연안어선은 커버리지를
이유로 제외했습니다. 20–30톤급 근해어선을 상정한 유사 선박군 정의(톤수대 × 어업종 ×
해역 × 계절)와도 맞지 않습니다.

세 가지 중 어느 쪽인지 알려주시면 좋겠습니다.

1. 매칭이 잘 되는 쪽이 원양어선이라 우선 3척만 뽑은 것이고, 근해어선도 매칭됨
2. 국제 식별자(IMO/Callsign) 보유율이 원양어선에 쏠려 있어 **근해어선은 구조적으로 매칭이 어려움**
3. 그 밖의 이유

2번이라면 이건 데이터 문제가 아니라 **기획 범위 문제**입니다. 발표에서 "근해어선 대상"
이라고 말하는데 실제로 계산되는 건 원양어선이면 질문을 받습니다. 팀 논의가 필요합니다.

**① 데이터 신선도 정보**

심사역 화면에 소스별 최종 갱신일을 표시하려 합니다 (GFW / 선박제원 / TAC / 해양기상). 심사역이 반드시 확인하는 항목입니다. 로더가 각 소스의 기준일자를 함께 반환해 주시면 그대로 붙이겠습니다.

**② 미확정 파라미터 5개는 여전히 대기 중입니다**

`CLAUDE.md`의 격자 크기 / 재방문 기간 / 유사군 최소 표본 / GAP 비율 임계값 / 매칭 신뢰도 임계값. 화면에서는 하드코딩하지 않고 설정값으로 빼두겠습니다. 실사 결과 나오면 공유 부탁드립니다.

`topPercent` 스칼라는 `scores`에서 파생 가능하므로 제거해도 되지만, 기존 코드 호환을 위해 당분간 함께 두는 것도 괜찮습니다. 의견 주세요.

### 김태윤의 샘플과 겹치지 않습니다

`sample_vessels.json` / `sample_events.json`은 **이벤트 단위** 실데이터이고,
`dashboard_mock.json`은 **선박 단위 산출 결과**라 층이 다릅니다. 파이프라인이 완성되면

```
sample_events.json → score/ → 선박 단위 산출 → 화면
```

으로 이어지고, `dashboard_mock.json`은 그 시점에 폐기됩니다. 김태윤 README에 적힌
*"BlueScore/A·B축/SHAP mock은 각 담당자가 제안서를 참고해 직접 만드는 게 맞다"* 에 따라
화면 담당이 만든 것이 `dashboard_mock.json`입니다.

대시보드 mock에 실제 3척을 쓰지 않은 이유는 위 ⓪번입니다 — 원양어선이고 조업 위치가
남대서양이라, 근해어선을 상정한 유사 선박군 정의와 독도·울릉도 인근 시연 화면에
맞지 않습니다.

## 3-1. 지금 돌아가는 것

`app.py`가 작성돼 실행됩니다.

```bash
pip install -r requirements.txt
streamlit run app.py
```

- 어업인 화면 `/` · 금융기관 화면 `/bank` — 두 주소를 미리 열어두면 시연 때 클릭 없이 전환됩니다
- 화면 하단에 **산출 경로(FastAPI·SQLite·체인 모드)** 가 항상 표시됩니다. 시연 중 무엇이 계산이고
  무엇이 임시값인지 숨기지 않기 위한 것입니다
- 선박 D(표본 부족)·E(매칭 실패)를 고르면 점수 영역이 사라지고 사유가 표시됩니다
- 지도는 Leaflet + Esri World Imagery(위성)이며 **API 키가 필요 없습니다**
- 시연 fixture를 바꾸면 FastAPI 시연 DB를 다시 seed한 뒤 두 화면에 같은 값이 반영됩니다.
  서버를 재시작할 필요 없습니다

## 4. 미결 사항

| 항목 | 필요한 결정 | 대기 대상 |
|---|---|---|
| 유사군 분포 반환 형식 | 위 3번 스키마 확정 | 김준기·오동규 |
| 축 간 트레이드오프 계수 | 값 또는 산출 방식 | 김준기·오동규 |
| 해시 함수 시그니처 | `chain/` 인터페이스 | 김준기·오동규 |
| 파라미터 5종 | 데이터 실사 결과 | 김태윤 |
| 새 상위 % 값 | 분포 확보 후 자동 결정 | — |
| 어업인 화면 모바일 대응 | 범위에 넣을지 | 팀 논의 |

어업인은 실제로는 선박에서 휴대폰으로 보게 됩니다. Streamlit 기본 반응형은 컬럼을 세로로 쌓기만 해서 2단 구성이 모바일에서 어떻게 무너지는지 확인이 필요합니다. 해커톤 범위에 넣을지 판단 부탁드립니다.
