## 뭘 했는지 (큰 단위로)

### 1. 선박 데이터 확보·매칭 — GFW ↔ 국내 데이터 연결

핵심 작업. GFW 조업 데이터를 가져오고, 그 선박들을 국내 공공데이터(선박제원, TAC)와 연결해서 톤수·마력 같은 실측값을 채워넣는 일련의 흐름.

- GFW API 연동(`gfw_client.py`) — 실제 호출로 파라미터명·페이지네이션 검증하며 재작성, `regions.mpa`(보호구역 필드) 실존 확인. 결과: 어업선박 31,605척, 이벤트 913,715건
- 국내 선박제원 매칭 — 수집(`collect_vessel_spec_candidates.py`) → 판정(`match_vessel_spec.py`) → 병합(`build_enriched_vessel_population.py`). 오동규가 중간에 이어받아 9,468척 100% 완료(그 과정에서 진행상태 카운터 중복집계 버그 발견/수정). 확정 663척(9.0%)
- **GFW 오분류 발견** — 확정매칭 663척 중 600척(90.5%)이 실제론 비어선. 어업선박 모집단 신뢰도 자체에 의문 제기, 팀 논의 대기
  - **(2026-08-15 추가) 원인 파악**: IMO/콜사인 완전일치 매칭에서도 오분류율 82~99%로 높게 나와 "매칭이 틀린 게 아니라 GFW 분류 자체가 문제"임을 확인. 표본 하나(자동차운반선 HYUNDAI 109 ↔ GFW상 "MORNING CAMILLA"/참치선망)를 실제 항적으로 대조해보니 GFW 쪽이 틀렸음이 확인됨 — AIS 자기신고 필드(선원이 수동 입력하는 IMO 등) 자체의 오류가 근본 원인으로 추정. 전수 검증은 항적을 사람이 봐야 해서 비용이 크므로 보류

- **(2026-08-15 추가) TAC 업종단위 집계로 기관출력 확보 대폭 확대**: 개별 이름매칭의 구조적 한계(정밀도 7.5~13.2%, 동명이인 문제)를 우회 — TAC를 업종별로 집계하고 GFW 자기신고 gear type을 다리로 삼아 매칭 없이 연결. 기관출력 확보 8척(0.03%)→13,908척(44.9%). 단 92.2%가 `gear_type_mapping_draft.py` 미확정 초안 기반이라 잠정치
- TAC 매칭(기관출력용) — 콜사인/IMO 없어서 이름만으로 매칭해야 했음. 로마자화 직접 구현, 상호 최고매칭 + 숫자분리비교로 오연결 줄임. 1차 93척 → MOF 비어선 표시와 교차검증해서 8척으로 정정 → 전체 418척으로 검증 확대(확실 18/사람확인 45/비어선제외 326/톤수차이 16/번호불일치 13) → 비어선 판정 vesselKind 표본검증까지 완료. 확정 8척 병합, 검토용 웹페이지 제작
