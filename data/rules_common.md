# BlueScore 데이터 수집 — 공통 규칙

담당: 김태윤


이 문서는 BlueScore 프로젝트에서 **어떤 외부 데이터 소스(GFW API, 국내
공공데이터포털 등)를 수집하든 공통으로 적용되는 규칙**을 담는다.

특정 소스만의 고유 규칙(엔드포인트, 파라미터 문법, 데이터셋 이름 등)은
이 문서 뒤에 소스별 섹션(예: "부록: GFW 전용 규칙")으로 이어 붙인다.
전부 김태윤 혼자 만들고 쓰는 개인 문서라 파일을 여러 개로 쪼갤
실익이 없어, 공통 규칙(번호 1~9)과 소스별 규칙을 한 파일에 같이
둔다 (2026-08-14: 원래 `rules_gfw.md`로 파일을 분리했었으나 통합).

**관련 문서**: `personal_notes.md` — GFW에 국한되지 않는 일반 작업
노하우(개인 참고용). 이 문서(공통 규칙 + GFW 규칙)와는 성격이 달라
따로 둔다.

---

## 1. 최상위 원칙

**수집과 가공을 절대 섞지 않는다.**

```
1단계: API 호출 → 응답을 가공 없이 그대로 저장     ← 모든 수집 코드가 여기까지만
2단계: 저장된 raw 데이터를 표로 펴기(평탄화)         ← 별도 규칙
3단계: 필터링, 분류, 판단 등 실제 가공              ← 별도 규칙
```

값을 읽고 판단하는 로직이 들어가는 순간 수집 코드의 책임 범위를
벗어난 것이다. "이거 필터링 아닌가?"라는 의심이 드는 순간 멈추고
재확인한다.

**이 원칙은 개인정보 배제보다 우선한다.** 응답에 개인정보 가능성이
있는 필드(예: 소유자명)가 포함돼 있어도, 수집 단계에서는 걸러내지
않고 원본 그대로 저장한다. 개인정보를 빼는 것도 하나의 "판단"이므로
필터링 단계의 책임이다. 다만 그런 필드가 존재하는지, 몇 건인지는
참고용 로그로 남겨 다음 단계 담당자가 알 수 있게 한다.

---

## 2. 저장 규칙

**형식: 원문 그대로.** 응답을 파싱해서 재직렬화하지 않는다. 원본이
JSON이면 JSON 텍스트 그대로, 다른 형식이면 그 형식 그대로 저장한다.
가공 없이 보존하는 게 원본 구조(중첩, 리스트, null vs 빈 문자열
같은 미묘한 차이)를 잃지 않는 유일한 방법이다.

**스냅샷 원칙: 재조회해도 기존 파일을 덮어쓰지 않는다.**

이유: 외부 API의 데이터는 소스에 따라 갱신 지연이 있을 수 있다(GFW
registry는 최대 2개월 지연 등, 소스별 상세는 각 소스 문서 참고).
"이 시점에 실제로 어떤 값이었는지"를 나중에 재현하려면, 새로 받은
데이터가 예전 데이터를 지워버리면 안 된다.

파일명에 조회 시각을 붙여서 스냅샷을 구분한다. 같은 시각에 재호출
되어 이름이 겹치면 접미사를 붙여서라도 절대 덮어쓰지 않는다.

**스냅샷을 읽는 코드는 파일명을 문자열로 고정하지 않고, 항상 "가장
최근 것"을 찾아서 쓴다** (2026-08-15 추가 — 원칙과 구현이 어긋나
있던 걸 발견해서 규칙으로 명문화). 스냅샷 원칙 때문에 파일명에
타임스탬프/날짜가 들어가는데, 그 파일을 읽는 다른 스크립트가
`MATCHES_PATH = ".../vessel_spec_matches__2026-08-13T....jsonl.gz"`처럼
특정 스냅샷 파일명을 문자열로 박아두면, 나중에 새 스냅샷이 생겨도
이 상수를 손으로 고치지 않는 한 계속 옛날 데이터를 읽는다 — 조용히
스테일해지는데 에러가 안 나서 알아채기도 어렵다. 실제로 7개 스크립트
(`match_tac_vessels.py`, `build_enriched_vessel_population.py`,
`attach_event_weather.py`, `collect_event_weather.py`,
`collect_vessel_spec_candidates.py` 등)에서 이 패턴이 발견됐다(발견
당시엔 결과가 우연히 최신 스냅샷과 일치해 문제가 드러나지 않았을
뿐, 구조적으로는 계속 위험했다). `data/snapshot_utils.py`의
`find_latest(directory, glob_pattern)`로 통일했다 — 새 스냅샷을 읽는
코드를 짤 때는 이 함수를 쓴다.

**저장 단위(폴더 등)를 응답 종류별로 분리한다.**

이유: 서로 다른 종류의 응답은 "무엇으로 식별되는가"가 다르다. 예를
들어 검색 결과는 쿼리 조건이 정체성이고, 상세 조회는 개별 ID가
정체성이다. 한곳에 섞으면 다음 단계(평탄화)에서 "이 묶음은 통째로
이 함수에 넣으면 된다"는 단순한 대응이 깨진다.

**메타데이터는 응답 본문과 분리해서 남긴다.**

요청 URL, 파라미터, 상태코드, 응답시간, 조회 시각 등은 응답 본문과
별도로 기록한다. 본문에는 절대 섞지 않는다 — 원본 오염 방지가 목적이다.

**소스별로 저장 경로를 분리한다.**

```
raw_data/
├── gfw/
├── domestic/
└── (새 소스)/
```

한 프로젝트 안에 여러 소스가 쌓이므로, 소스가 섞이지 않도록 최상위
경로부터 나눈다.

## 3. 재시도 / 실패 처리 규칙

**재시도 대상:** 429, 500, 502, 503, 524
**재시도 정책:** 최대 3회, 대기 간격 2초 → 4초 → 8초 (지수 백오프)
**재시도하지 않는 것:** 401 등 인증/요청 자체가 잘못된 경우 — 재시도
해도 같은 결과이므로 즉시 실패 처리하고 다음으로 넘어간다.

**한 건의 실패가 전체를 멈추지 않는다.** 예를 들어 300건 중 5번째
항목 조회가 3회 재시도 후에도 실패하면, 그 항목은 실패로 기록하고
6번째로 넘어간다. 전체 수집이 중단되지 않는다.

이 정책은 기본값이다. 특정 소스가 별도의 제약(예: 동시 요청 수 제한)
을 갖고 있으면 그 소스의 문서에 추가로 기록한다.

---

## 4. 인증 규칙

토큰/API 키를 코드에 하드코딩하지 않는다. `.env` 파일에서 읽되, 이
파일은 반드시 `.gitignore`에 포함해 저장소에 커밋되지 않도록 한다.

우선순위: 환경변수가 이미 설정돼 있으면 그것을 쓰고, 없으면 `.env`
파일에서 읽는다.

여러 소스의 키를 한 `.env` 파일에서 관리한다:
```
GFW_API_TOKEN=...
DATA_GO_KR_API_KEY=...
```

## 5. 조회 기간

시간 범위가 필요한 수집(예: 이벤트, 활동 기록)은 자동으로 범위를
계산하지 않는다 — **실행할 때마다 어느 기간을 받을지 직접 정한다.**
(2026-08-14: 이전엔 "직전 완결 반기 시작일 ~ 오늘"을 매번 자동
계산하는 반기 단위 규칙이 있었으나, 실행할 때마다 겹치는 몇 달치를
통째로 재호출하는 비용이 커서 폐기. 언제부터 언제까지 받을지는
그때그때 수동으로 결정한다.)

날짜를 코드에 고정값으로 박아넣지 않는 것(4번 인증 규칙과 같은
이유로 소스 코드를 안 고치고 바꿀 수 있어야 함)은 여전히 지킨다 —
실행 시점에 파라미터/인자로 넘긴다.

---

## 6. 진행 상태 기록 (중단 후 재개)

수집 도중 네트워크가 끊기거나 강제 종료돼도, 다시 실행하면 이어서
진행할 수 있어야 한다. 이미 완료된 항목은 건너뛰고 남은 것만 처리한다.

단, 조회 조건(기간 등)이 지난 실행과 다르면 조용히 이어받지 않고
새로 시작한다 — 서로 다른 조건의 진행 상태가 뒤섞이면 안 된다.

매번 처음부터 전체를 다시 수집하는 구조는 이 규칙 위반이다.

---

## 7. 검증 규칙 (수집 후 자동 점검)

수집이 끝나면 아래를 자동으로 점검한다. 하나라도 위반되면 명확히
실패로 표시하고, 이 실행분의 raw 데이터를 다음 단계로 넘기지 않는다.

**모든 소스 공통 하드 게이트:**
1. 저장된 데이터가 원본 구조 그대로인가 (일부 필드만 남긴 흔적 없는가)
2. 검색/목록 조회로 나온 전체 항목 수와 실제 상세조회를 시도한 항목
   수가 일치하는가. 불일치가 있다면 그 항목들이 실패로 기록되어 사유가
   설명 가능한지 확인한다 (이유 없이 조용히 누락되면 위반).
3. 재조회 시 기존 스냅샷 파일이 삭제·덮어쓰기 되지 않았는가
4. 토큰/인증 정보가 저장된 데이터 파일 어디에도 노출되지 않았는가
   (본문뿐 아니라 메타데이터 파일도 포함)

**정보성 체크 (통과/실패 판정 없음, 참고 로그만):**
- 개인정보 가능성이 있는 필드가 몇 건 포함됐는지

소스별로 추가 게이트가 필요하면 각 소스 문서에 덧붙인다.

**게이트가 위반을 잡았을 때, 게이트 자체를 완화해서 통과시키지
않는다.** 원인이 된 실제 코드를 고친다. 예외적으로 원칙 자체를
재조정해야 할 상황이면, 그 판단과 이유를 문서에 명시적으로 기록하고
규칙을 개정한다 — 말없이 코드만 바꾸지 않는다.

## 8. 새 소스를 추가할 때

1. 이 문서 끝에 "부록: {소스명} 전용 규칙" 섹션을 새로 추가한다
   (번호 충돌을 피하려면 소스 접두어를 붙인다 — GFW 부록은 G1, G2...
   처럼). 공통 규칙(1~9번)과 같은 파일에 두되, 번호 체계만 분리한다.
2. 그 소스만의 고유 규칙(엔드포인트, 파라미터 문법, 데이터셋 이름,
   소스별 지연시간, 소스별 추가 게이트 등)만 부록 섹션에 적는다.
3. 코드에서 공통 로직(재시도, 원문 저장)은 기존 공통 모듈을 재사용
   하고, 소스 고유 로직만 새로 짠다. 완전히 새로운 코드를 처음부터
   다시 짜지 않는다.
4. **파라미터 문법 등 문서만으로 확정되지 않는 부분은, 코드를 다 짜기
   전에 소규모로 실제 호출해서 먼저 확정한다.** 확정 안 된 채 대량
   수집을 시작하지 않는다.

5. **문법 확정 단계에서 토큰(비용)을 절약하는 방법:**
   - 문서(특히 JS로 렌더링되는 API 문서 사이트)를 웹에서 여러 번 재조회
     하기보다, **실제 API에 최소 비용(작은 limit)으로 sanity call을
     먼저 던져 확인하는 쪽이 더 빠르고 싸다.** 문서 페이지는 요약 도구를
     거치면서 실제 예시 코드나 파라미터 제약(허용 범위, 필수 여부 등)이
     누락되기 쉽다 — 반면 API가 돌려주는 4xx 에러 메시지에는 그 정보가
     그대로 들어있는 경우가 많다.
   - 확인할 조합이 여러 개면(예: 파라미터명 A/B × 따옴표 종류 2가지),
     전부를 무작정 다 시도하지 않는다. 문서/사례로 봤을 때 가장 유력한
     조합 하나를 먼저 시도하고, 그 결과(성공/실패, 에러 메시지)를 보고
     다음에 무엇을 좁혀서 시도할지 정한다.
   - 200 응답이 왔다고 끝난 게 아니다. **응답 바디를 실제로 열어서
     의도한 필터/조건이 적용됐는지 확인한다.** (예: 200이지만 조건이
     자유 텍스트로 처리되어 엉뚱한 결과가 섞여 나오는 경우가 있음 —
     상태 코드만으로 문법이 맞다고 판단하지 않는다.)
   - 4xx 에러 메시지(400, 422 등)를 무시하지 않는다. 파라미터명이나
     허용 범위(예: "limit must not be greater than 50", "property
     offset should not exist")처럼 다음 시도를 바로 좁혀주는 정보가
     들어있는 경우가 많다.
   - 페이지네이션 방식(offset 기반인지, 커서/토큰 기반인지)도 문서로
     추측하지 말고 위와 같은 방식으로 실제 호출 1~2회로 확정한다 —
     대량 수집 코드를 다 짜고 나서 방식이 틀렸다는 걸 알게 되면 그
     비용이 훨씬 크다.

## 9. 이 규칙을 어긴 것으로 간주되는 사례 (체크리스트)

코드 작성/리뷰 시 아래에 해당하면 규칙 위반이다.

- [ ] 응답을 받은 즉시 파싱해서 필요한 값만 뽑고 원본을 버림
- [ ] 특정 조건으로 일부 항목을 수집 대상에서 제외
- [ ] 재조회 시 기존 파일을 덮어씀
- [ ] 스냅샷 파일을 읽는 코드에서 파일명을 문자열로 고정함(`find_latest()` 안 씀)
- [ ] 서로 다른 종류의 응답을 구분 없이 한곳에 저장
- [ ] 하나의 요청 실패로 전체 수집 프로세스가 종료됨
- [ ] 토큰이 코드 파일 안에 문자열로 박혀 있음
- [ ] 조회 기간을 코드에 고정값으로 박아넣음
- [ ] 소스 고유 문법을 확인 없이 추측만으로 코드에 반영함
- [ ] 하드 게이트가 실패했을 때 게이트를 느슨하게 고쳐서 통과시킴
- [ ] 새 소스 코드를 짤 때 기존 공통 모듈을 안 쓰고 처음부터 복붙해서 새로 짬

병합. 번호 충돌을 피하려고 이 부록 섹션만 `G` 접두어를 쓴다 — 위
공통 규칙 번호(1~9)는 그대로 유지된다.)

아래는 GFW(Global Fishing Watch) API에만 해당하는 규칙이다. 위
공통 규칙(1~9번)을 전제로 하고, 그 위에 GFW 고유의 것만 얹는다.

---

## G1. 수집 대상 범위

**한다:**
- Vessels Search API — 한국 국적(`flag='KOR'`) **어업 선박**(`combinedSourcesInfo.shiptypes.name='FISHING'`) 목록 전체 (2026-08-13 범위 확정, 근거는 G2-1번 참고)
- Events API — 위 목록의 distinct vesselId 전체(32,105개), 이벤트 타입
  5종(FISHING, GAP, PORT_VISIT, ENCOUNTER, LOITERING)을 한 호출에 동시 요청
- Vessels 상세 API — **이벤트가 1건 이상 있었던 vesselId 우선**
  (9,723개, 2026-08-13 우선순위 확정, 근거는 G2-2번 참고). 순서도
  Search → Events → 상세조회로 바뀜(원래 상세조회가 2단계였으나 Events
  결과로 상세조회 대상을 좁히기 위해 순서를 바꿈).

**하지 않는다 (다음 단계로 미룬다):**
- 4Wings(격자 단위 조업효과) API
- Regions API로 EEZ id 조회 — 아래 G2번 이유로 이번 단계에서 불필요

## G2. 선박 목록 확보 방법

**왜 EEZ(위치) 기준이 아니라 국적(flag) 기준인가**

| 방법 | 걸리는 조건 | 문제 |
|---|---|---|
| 한국 EEZ 위치로 필터 | 위치 | 중국·일본 배도 한국 해역에서 조업하면 같이 잡힘 |
| 4Wings로 조업 이벤트 있는 배만 | 국적 + 이벤트 발생 | 등록만 돼 있고 최근 조업 이벤트가 없는 배는 누락 |
| **Vessels Search, `flag='KOR'`** | **국적 자체** | 등록부 자체를 직접 조회 — 조업 여부·위치 무관하게 전체 모집단 확보 |

Vessels Search를 1순위로 쓴다. 이게 "한국 국적으로 등록된 전체 어선"
이라는 분모를 만들고, 이후 Events 조회에서 실제로 데이터가 잡히는
배가 분자가 된다. 이 분모/분자 비율 자체가 나중에 유용한 지표가 된다
— 등록은 됐는데 AIS 데이터가 안 잡히는 배가 얼마나 되는지 알 수 있다.

## G2-1. 어업 선박(FISHING)으로 범위 좁히기 (2026-08-13 결정)

**배경:** `flag='KOR'` 단독 조건으로 조회하면 89,897척이 나오는데,
BlueScore는 어업 선박만 필요하다. 이 프로젝트는 어업 선박이 아닌
선종(화물선, 여객선, 벙커선 등)까지 raw로 받을 이유가 없으므로,
"무엇을 수집 대상으로 삼을지"를 정하는 범위 결정으로서 국적 조건에
어업 선박 조건을 추가한다. (raw 원칙 위반 아님 — 대상 범위 설정과
받은 데이터를 가공하는 것은 다른 문제. 공통 규칙 1번 참고.)

**시도 1: datasets 파라미터로 fishing-vessels만 지정 — 안 됨.**
`public-global-fishing-vessels:latest` 등 3종 데이터셋명은 이미
G7번 표에서 404로 확인됨. v3 Vessels Search의 `datasets`는
`public-global-vessel-identity:latest` 하나만 유효하다. 즉 데이터셋
단위로 어업 선박만 서버가 걸러주는 방법은 없다.

**시도 2: where 절에 선종 조건 추가 — 됨.** `where`에 존재하지
않는 필드를 넣으면(예: `shiptypes`) 422 에러가 나는데, 그 에러
메시지가 **허용된 필드 전체 목록**을 그대로 알려준다:

```
id, registryLastUpdateDate, shipname, nShipname, ssvid, callsign, imo,
flag, geartypes, transmissionDateFrom, transmissionDateTo,
combinedSourcesInfo.shiptypes.name, combinedSourcesInfo.geartypes.name,
selfReportedInfo.id, selfReportedInfo.shipname, selfReportedInfo.nShipname,
selfReportedInfo.ssvid, selfReportedInfo.callsign, selfReportedInfo.imo,
selfReportedInfo.flag, selfReportedInfo.transmissionDateFrom,
selfReportedInfo.transmissionDateTo, registryInfo.shipname,
registryInfo.nShipname, registryInfo.ssvid, registryInfo.callsign,
registryInfo.imo, registryInfo.flag, registryInfo.geartypes,
registryInfo.recordId, registryInfo.transmissionDateFrom,
registryInfo.transmissionDateTo, registryOwners.name,
registryTmtExtraFields.masterEntityId
```

이 중 선종 분류에 쓸 수 있는 필드는 두 개이고, **의미가 다르다**:

| 필드 | 의미 | `='FISHING'`으로 걸었을 때 (flag='KOR' 기준) |
|---|---|---|
| `combinedSourcesInfo.shiptypes.name` | 등록부+AIS 결합 추정 **선종 분류**(FISHING/CARGO/PASSENGER/CARRIER/BUNKER/OTHER/NA 등) | **total 31,605건** — 이전에 수집된 raw 표본(36,600건) 클라이언트 집계로 나온 비율(34.5%)과 거의 정확히 일치 (89,897 × 34.5% ≈ 31,014) → 신뢰도 높음 |
| `geartypes` (바로 이 이름, registryInfo.geartypes와 combinedSourcesInfo.geartypes.name에 OR로 확장됨) | 조업 **방식/장비** 분류(TRAWLERS, TUNA_PURSE_SEINES 등)이며 일부만 값이 "FISHING"으로 뭉뚱그려 들어있음 — 선종 판별용이 아님 | total 9,931건 — `shiptypes` 결과와 다른 개념이라 채택 안 함 |

**채택한 조건:** `where=flag='KOR' AND combinedSourcesInfo.shiptypes.name='FISHING'`
(서버가 `(selfReportedInfo.flag='KOR' OR registryInfo.flag='KOR') AND
combinedSourcesInfo.shiptypes.name='FISHING'`로 정규화해서 처리함을
응답 metadata.query로 확인). **total = 31,605건** (2026-08-13 기준).

**기존에 진행 중이던 `flag='KOR'` 단독 수집(89,897척 대상)은
48,800건(976페이지)까지 받은 상태에서 의도적으로 중단.** 이미 저장된
raw 파일은 삭제·수정하지 않고 `raw_data/gfw/vessels_search/flag_KOR__2026-08-13T07-23-02.173Z/`에
그대로 보존(그 폴더의 `_progress.json`에 중단 사유 기록). 이후 수집은
`flag_KOR_shiptype_FISHING__*` 폴더에서 새 스냅샷으로 진행한다.

## G2-2. 상세조회 우선순위: 이벤트 있는 배 먼저 (2026-08-13 결정)

**배경:** Events 수집(3단계) 결과, 어업 선박 distinct vesselId
32,105개 중 2026-01-01~08-13 기간에 이벤트가 1건이라도 있는 배는
9,723개(30.3%)뿐이었다. 나머지 22,382개(69.7%)는 등록은 돼 있지만
이 기간 동안 FISHING/GAP/PORT_VISIT/ENCOUNTER/LOITERING 어느 것도
잡히지 않았다.

**결정:** 상세조회(2단계, 순서상으로는 Events 다음)를 32,105개
전체가 아니라 이벤트가 있었던 **9,723개부터 먼저** 진행한다.

**이건 값 기반 필터링이 아니라 구조적 우선순위 결정이다.** 톤수,
근해/연안 여부 같은 속성으로 일부를 골라내는 것과는 다르다 —
이벤트가 0건인 배는 애초에 이벤트 기반으로 계산하는 후속 지표(A/B축
등) 자체가 성립하지 않으므로, 상세조회 리소스를 우선순위가 높은
쪽(이벤트가 있어서 실제로 지표 계산에 쓰일 배)에 먼저 투입하는
것뿐이다. 공통 규칙 1번의 "필터링 금지" 원칙과 충돌하지
않는다 — 대상에서 빼는(exclude) 게 아니라 순서를 뒤로 미루는
(defer) 것이다.

**22,382개(이벤트 0건)는 영구 제외가 아니라 보류다.** 이 vesselId
들은 1단계(Vessels Search) raw 데이터에 그대로 남아있으므로, 언제든
필요하면 이어서 상세조회할 수 있다. 이미 32,105개 전체를 대상으로
시작했던 상세조회 실행(`vessel_detail__2026-08-13T08-16-00.192Z`,
1,357건 부분완료)도 삭제하지 않고 그대로 보존했다 — 나중에 22,382개
쪽을 마저 진행할 때 이미 받은 건 건너뛰고 재사용된다.

**대상 목록 출처(2026-08-14 기준):** `data/raw/gfw_events_2026-01-01_2026-08-13.jsonl.gz`의
distinct `vesselId`. 원래 출처였던 개인 작업 폴더의 파일은 정리 과정에서
삭제됐지만, 이벤트 원본 파일에서 재계산해도 동일한 9,723개가 나옴을
확인했다 (`data/collect_vessel_spec_candidates.py`의 `load_target_vessels()`
참고). "재계산하지 않고 그대로 읽는다"는 원래 취지(이벤트 있음의 정의를
3단계와 항상 일치시킴)는 지금도 유효하다 — 소스 파일 위치만 바뀌었다.

## G3. GFW 고유 지연 시간 (조회 기간을 수동으로 정할 때 참고할 값)

- Vessels registry: 최대 2개월 지연
- Events: 최대 72시간 지연

이 지연이 있기 때문에 스냅샷 원칙(공통 규칙 2번)이 특히 중요하다.
"이 시점에 실제로 어떤 값이었는지"를 나중에 재현하려면, registry가
갱신되기 전 값도 남아있어야 한다. 조회 시작일을 너무 최근으로 좁게
잡으면 이 지연 때문에 최근 구간의 registry 갱신분을 놓칠 수 있다는
점도 고려해서 기간을 정한다.

## G4. Events 호출 시 효율 규칙

**이벤트 타입을 하나씩 나눠 호출하지 않는다.** GFW Events API는 한
번의 호출에 여러 이벤트 타입을 동시에 요청할 수 있다.

```
잘못된 방법 (호출 5배):
  선박 1척당 FISHING 호출 1번 + GAP 호출 1번 + ... = 5번 호출

옳은 방법 (호출 1번):
  선박 1척당 5개 이벤트 타입을 한 호출에 동시 요청
  → 1번의 호출로 5종 이벤트를 동시에 받음
```

이유: "raw는 다 받는다"는 원칙과 "불필요하게 호출 횟수를 늘리지
않는다"는 효율성이 이 방식으로 동시에 만족된다.

**페이지네이션은 자동으로 끝까지 순회한다.** 응답의 전체 건수와
현재 받은 건수를 비교해서, 아직 안 받은 데이터가 남아있으면 다음
페이지를 계속 요청한다. 첫 페이지만 받고 멈추지 않는다.

## G5. GFW 고유 API 제약

**4Wings API는 유저당 활성 리포트 1개만 허용**, 동시 요청 시 429.
리포트 생성 100초 초과 시 524 타임아웃. (이번 단계는 4Wings를
다루지 않으므로 참고만, 이후 확장 시 적용.)

## G6. GFW 전용 검증 게이트 (공통 규칙 7번에 추가)

공통 하드 게이트 4개(원본 보존, 무설명 누락 금지, 스냅샷 보존, 토큰
비노출)에 더해, GFW 수집에서는 아래를 정보성으로 기록한다.

**정보성 체크 (통과/실패 판정 없음):**
- `registryOwners`(선박 소유자명 등 개인정보 가능) 포함 여부와 건수
  — 공통 규칙 1번의 "개인정보 배제보다 원본 보존 우선" 원칙에 따라
    이번 단계에서는 하드 게이트로 만들지 않는다.

## G7. 확인되지 않은 사항 (실행 전 실제 호출로 확정할 것)

아래는 공식 문서만으로는 확정되지 않았다. 코드를 짜기 전에 실제
API를 소규모로 호출해서 먼저 확정하고, 그 결과를 이 문서에 반영한다.

| 항목 | 상태 |
|---|---|
| Vessels Search에서 국적 조건(`flag='KOR'`)을 걸 때 쓸 정확한 파라미터명 | **확정: `where=flag='KOR'`** (2026-08-13 실제 호출로 검증). `query`는 SQL 조건식을 해석하지 않고 자유 텍스트 토큰 검색으로 처리됨 — `query=flag='KOR'`을 보내면 `FLAGKOR`로 정규화되어 flag가 KOR이 아닌 배(예: flag=IND, shipname="KOR")까지 섞여 나옴 (200 응답이지만 오답). `where=flag='KOR'`은 작은따옴표/큰따옴표 둘 다 200을 반환하며 결과가 동일함 — API가 내부적으로 `(selfReportedInfo.flag='KOR' OR registryInfo.flag='KOR')`로 정규화해 두 표기를 동등하게 처리함. total=89,897건. **datasets 값도 함께 확정**: 이 작업지시서에 있던 3종(`public-global-fishing-vessels:latest`, `public-global-carrier-vessels:latest`, `public-global-support-vessels:latest`)은 v3 Vessels Search에서 404(Not Found)를 반환함 — 존재하지 않는/무효한 데이터셋명. 공식 문서(api-doc.globalfishingwatch.org) 및 실호출로 확인된 올바른 값은 단일 통합 데이터셋 `datasets[0]=public-global-vessel-identity:latest` 하나뿐임. |
| GFW 계정의 실제 quota(총 호출 한도) | 공식 문서에서 수치 확인 안 됨 — 계정 대시보드에서 별도 확인 권장 |
| 한 번의 Events 호출로 5개 타입이 정말 동시에 오는지 | 문서의 실제 예시에 근거한 추정, 실제 응답으로 검증 필요 |
| Vessels Search 페이지네이션 방식과 페이지당 최대 건수 | **확정** (2026-08-13 실제 호출로 검증). `offset` 파라미터는 존재하지 않음 — 보내면 422 (`"property offset should not exist"`). 응답 바디에 포함된 `since` 값(커서 토큰)을 다음 요청의 `since` 파라미터로 그대로 넘기는 커서 기반 페이지네이션만 지원함. `limit` 최대값은 50 — 51 이상 요청 시 422 (`"limit must not be greater than 50"`). `flag='KOR'` 조건 기준 `total`은 약 89,897건이므로 완주하려면 페이지 약 1,798회(순차 호출, 이전 페이지의 `since` 없이는 다음 페이지를 못 받으므로 병렬화 불가) 필요. `since` 토큰은 서버 측 스크롤 컨텍스트로 추정되며, 장시간 중단 후 재개 시 만료돼 있을 가능성이 있음 — 재개 시도 시 이 가능성을 염두에 둘 것 (만료됐다면 처음부터 새 스냅샷으로 다시 시작). |

**이 표를 채우지 않은 채로 대량 수집을 시작하지 않는다.** 먼저 선박
소수(1~5척 수준)로 시험 호출해서 표의 각 항목을 확정한 뒤, 확정된
방식으로 전체 수집을 진행한다 (공통 규칙 8번 참고).

## G9. 실무 빠른 참고 (구 `gfw_collection_notes.md`)

`data/gfw_client.py`를 만들고 고치는 과정에서 확인한, GFW API를
다시 다룰 때 가장 자주 찾아보게 되는 것만 추린 요약이다. 근거/시행
착오 과정은 위 G1~G8 참고.

**확인된 API 동작 (실제 호출로 검증됨):**
- **Vessels Search(`GET /v3/vessels/search`)**: 조건 필터링은 `query`가 아니라
  `where` 파라미터로 해야 정확하다. `query=flag='KOR'`는 자유 텍스트 토큰
  검색으로 처리되어 `FLAGKOR`로 정규화되고, flag가 KOR이 아닌 선박까지 섞여
  나온다 (200 응답이지만 오답). 페이지네이션은 `offset`이 아니라 응답의
  `since` 커서 토큰을 다음 요청에 그대로 넘기는 방식이며, `limit` 최대값은 50.
- **Events(`GET /v3/events`)**: POST가 아니라 GET이고, 날짜 파라미터는
  camelCase가 아니라 kebab-case(`start-date`/`end-date`)의 URL 쿼리다.
  이벤트 타입 5종(FISHING/PORT_VISIT/ENCOUNTER/LOITERING/GAP) 데이터셋을
  `datasets[0..4]`로 한 번에 동시 요청할 수 있다. `vessels[]` 배열로 선박을
  최대 20개까지 한 호출에 배치할 수 있다(21개부터 422). 페이지네이션은
  `offset`/응답의 `nextOffset`.
- **Vessels 상세조회(`GET /v3/vessels/{id}?dataset=...`)**: 선박 1척의
  registryInfo/selfReportedInfo를 재확인하는 별도 엔드포인트. 현재
  `data/gfw_client.py`엔 이 기능을 넣지 않기로 함 — search_vessels 결과와
  대부분 겹치고, 스코어 계산이 이 필드를 쓰지 않아서 지금은 불필요하다고
  판단(2026-08-13). 나중에 GFW 공식 등록부 매칭 여부 자체를 신호로 쓰기로
  하면 그때 추가.

**재시도/배치 정책:**
- 재시도 대상: 429, 500, 502, 503, 524 (최대 3회, 2s→4s→8s 백오프) — 공통 규칙 3번과 동일
- 재시도 안 함: 401 등 인증/요청 오류 (재시도해도 같은 결과)
- Events 배치 크기: 20척/호출 (`EVENTS_BATCH_SIZE`)

**연혁 참고:** 이 지식은 원래 개인 임시 작업 폴더에서 실제 API를
여러 번 호출해 확인한 것이다. 그 폴더는 2026-08-14 정리 과정에서
삭제됐고, `rules_gfw.md`·`gfw_collection_notes.md`였던 내용을
전부 이 문서(`rules_common.md`)로 병합했다.

`data/raw/gfw_vessels_kor_fishing__2026-08-13.jsonl.gz`(31,605건)와
`data/raw/gfw_events_2026-01-01_2026-08-13.jsonl.gz`(913,715건)도
그 폴더에 이미 받아뒀던 원본 스냅샷(API 재호출 없이)을 오프라인으로
정규화해서 옮겨온 결과다 — 이 변환에 썼던 1회성 스크립트는 폴더
삭제와 함께 더 이상 실행할 수 없어 같이 정리했다.
