## 한 줄 요약

GFW·국내 선박제원·TAC·해양기상 데이터를 모두 실제로 확보/검증했습니다. A축은 바로 실행 가능하고, B축(LightGBM)을 막고 있던 두 가지(해양기상 부착, 어업종 매핑)도 초안 수준까지 왔습니다. 오늘 오후 TAC를 업종 단위로 집계하는 방식을 추가해서 기관출력(마력) 확보 대상을 8척→13,908척(44.9%)로 크게 늘렸는데, **이 숫자는 아직 팀이 확정 안 한 어업종 매핑 초안에 92.2% 의존하고 있어 확정 수치가 아닙니다** — 아래 4번이 이제 가장 급한 팀 결정 사항입니다. 남은 건 팀이 결정할 것 2가지(어업종 매핑 확정, GFW 오분류 대응)와 외부 응답 대기 2가지(연안AIS 키, 기관출력 단위)입니다.

## 2. 선박 매칭 결과

### 국내 선박제원 매칭

국내 공공데이터의 선박 정보(콜사인·IMO·이름 등)와 GFW 선박을 연결한 결과입니다. 9,468척 전체를 다 확인했고:

| 방식 | 척수 | 비율 |
|---|---:|---:|
| IMO 번호 완전 일치 | 34 | 0.5% |
| 콜사인 완전 일치 | 187 | 2.6% |
| 이름이 충분히 비슷함(확정) | 442 | 6.0% |
| 이름이 애매하게 비슷함(채택 안 함) | 3,806 | 51.9% |
| 아예 못 찾음 | 2,858 | 39.0% |
| **확실히 연결된 것 합계** | **663** | **9.0%** |

### TAC 데이터 매칭 (마력 정보 확보용)

TAC(어종별 할당량) 데이터에는 국내 선박제원에 없는 **기관출력(마력)** 값이 있어서, GFW 선박과 연결하려고 시도했습니다. 문제는 TAC에 콜사인·IMO 같은 고유번호가 없어서 **선박 이름만 보고 연결**해야 했다는 점입니다 — "OO호"처럼 흔한 이름이 많아서 다른 배로 잘못 연결될 위험이 컸습니다.

이름이 서로 제일 잘 맞는 짝끼리만(양쪽에서 서로를 1순위로 지목할 때만) 인정하는 방식으로 418척을 찾았습니다. 그런데 국내 선박제원 데이터의 "이 배는 등록상 어선이 아닐 수 있음" 표시와 대조해보니, **418척 중 326척(78%)이 실제로는 화물선·예선 같은 비어선**과 겹쳐 있었습니다. 이 표시가 맞는지 직접 하나씩 확인해봤는데, 부선·석유제품운반선·화물선·예선류 등 정말로 비어선이 맞았습니다 — 즉 이름만으로 연결하면 열에 여덟은 다른 배로 잘못 연결된다는 뜻입니다.

최종 판정:

| 판정 | 척수 | 뜻 |
|---|---:|---|
| 확실히 맞음(accept) | 18 | 선박번호도 일치하고, 비어선 의심 표시도 없고, 톤수도 비슷함 |
| 사람이 봐야 함 | 45 | 자동으로는 판단이 안 됨 — 아래에서 설명 |
| 사실 비어선(제외) | 326 | 국내 데이터의 "비어선 의심" 표시와 겹침(직접 확인해서 맞다고 검증함) |
| 톤수 차이가 너무 큼(제외) | 16 | 나머지 조건은 맞았지만 톤수가 30% 넘게 다름 |
| 선박번호가 다름(제외) | 13 | 이름은 비슷한데 번호가 안 맞음 |

**"사람이 봐야 함" 45척 중 44척은 국내 선박제원 데이터에 그 배 기록 자체가 없어서**, 자동으로 확인할 방법이 원천적으로 없는 경우입니다(매칭 품질이 의심스러운 게 아니라 단순히 대조할 자료가 없는 것). GFW가 스스로 신고한 어업 종류를 참고 자료로 붙여서 `data/tac_needs_human_review_45.md`에 표로 정리해뒀습니다 — **팀원 아무나 훑어보고 accept/reject만 표시하면 됩니다.**

- 검토용 웹페이지(필터·정렬 가능): https://claude.ai/code/artifact/e262a413-3a28-4b5e-bc11-cfbe0ad1cc4d
- **메인 데이터에는 가장 확실한 8척만 반영 완료**(`data/merge_tac_into_enriched.py`). 그중 5척은 기존 톤수 값과 달라서 "충돌 있음"으로 표시만 해두고 임의로 덮어쓰지 않았습니다.

### (신규, 2026-08-15) TAC 업종단위 집계 — 이름매칭 우회

이름매칭(위 8척)은 정밀도가 7.5~13.2%에서 안 올라가는 구조적 한계가 있습니다(`BlueScore_TAC매칭_임계값_실측분석.md`) — TAC에 콜사인/IMO 같은 고유식별자가 없어서 근본적으로 못 푸는 문제입니다.

그래서 개별 매칭 대신 **업종(어업 종류) 단위로 통째로 집계**하는 방식을 추가했습니다(`aggregate_tac_by_gear_type.py`) — 선박 이름 비교가 아예 없으니 동명이인 문제 자체가 없습니다:

1. TAC를 "할당 어업 종류 명"으로 그룹지어 평균 톤수·마력 계산
2. GFW 선박이 스스로 신고하는 gear type(`fishingType`, 예: TRAWLERS)을 국내 어업종에 역매핑
3. 매칭된 GFW 선박에 해당 업종의 평균값을 부여

결과: **기관출력 확보 8척(0.03%) → 13,908척(44.9%)**. 단, **이건 개별 선박 정밀값이 아니라 업종 평균값**입니다 — 같은 gear type인 배들은 전부 같은 톤수·마력을 갖게 됩니다. score팀이 유사 선박군(톤수대×어업종×해역×계절) 상대비교에 쓸 때 이 점을 감안해야 합니다.

**⚠ 더 중요한 제약**: 이 매핑의 근거인 `gear_type_mapping_draft.py`가 아직 팀 확정 전 초안입니다(4번 참고). TAC 표본 1,898척 중 **92.2%(1,750척)가 "approximate"(불확실) 등급 매핑**을 거쳐 나온 값이에요 — 예를 들어 국내 트롤 계열 6개 어업종이 GFW `TRAWLERS` 하나로 뭉뚱그려집니다. **즉 44.9%는 4번 매핑표가 확정되기 전까지는 잠정치입니다.**

## 3. ⚠️ 중요 발견: GFW가 "어업선박"이라 부른 것 중 진짜 어업선박이 아닌 게 많음

국내 선박제원과 확실히 연결된 663척 중 **600척(90.5%)이 국내 등록부 기준으로는 어선이 아닙니다** — 석유제품운반선·일반화물선·자동차운반선·준설선·예선·유조선 등입니다. GFW가 "이 배는 어업선박이다"라고 분류한 기준이 한국 선박에 대해서는 꽤 부정확할 수 있다는 뜻입니다.

**팀 논의 필요**: GFW의 어업선박 목록(31,605척)을 그대로 쓸지, 걸러내고 쓸지 정해야 합니다.

### (신규, 2026-08-15) 추가 신호: GFW 자기모순 라벨 25척

위 90.5%는 MOF 매칭이 된 배(9,468척 대상)만 확인 가능했는데, GFW 응답 자체에서 MOF 매칭 없이도 즉시 쓸 수 있는 신호를 하나 더 찾았습니다(`filter_self_contradicting_labels.py`). "어업선박"으로 분류된 배 중 자기 자신의 `fishingType`(자기신고 gear type)에 CARGO/PASSENGER/CARRIER가 그대로 들어있는 경우 — 예: `VITIM`(CARGO), `KOREA PRINCESS`(PASSENGER). 이런 배는 GFW 스스로도 앞뒤가 안 맞는 셈이라 신뢰도 낮은 신호입니다. 전체 31,005척 중 25척(0.08%) 발견했고, `master_vessel_registry`에 삭제가 아니라 `gfwSelfContradictingFlag`로만 표시해뒀습니다 — 실제로 걸러 쓸지는 3번 논의 결과에 맞춰 결정하면 됩니다.

## 4. 국내→GFW 어업종 매핑 (초안)

`data/gear_type_mapping_draft.py` — 국내 19개 어업 종류를 GFW 분류에 대응시킨 초안입니다:

- **바로 연결됨(9개)**: 자망→SET_GILLNETS, 통발→POTS_AND_TRAPS, 트롤→TRAWLERS 등
- **애매함(8개)**: GFW 분류가 국내보다 더 뭉뚱그려져 있어서 확정 못함 — 예를 들어 외끌이/쌍끌이/동해구 저인망이 GFW에서는 전부 TRAWLERS 하나로 합쳐짐
- **대응 안 됨(2개)**: 잠수기어업(그물·낚시 장비 자체를 안 씀), 연안복합어업(여러 어법을 겸업해서 하나로 못 정함)

**팀 회의에서 확정 필요** — 자동으로 판단할 수 없는 도메인 지식이 필요한 부분입니다.

**⚠ (2026-08-15 추가) 이제 이 확정이 더 급해졌습니다** — 위 2번의 "TAC 업종단위 집계"가 이 매핑표를 그대로 씁니다. "애매함(8개)" 항목이 기관출력 확보 13,908척 중 92.2%를 차지하고 있어서, 이 8개를 확정하기 전까지는 44.9%라는 숫자를 score팀에 확정치로 전달하면 안 됩니다.

## 4-1. (신규) 이벤트 지속시간 이상치 — GAP 아니라 port_visit 오탐이었음 (정정)

이전에 조업이벤트 913,715건 중 6,650건(0.73%, 최장 5,082일=14년)을 "GAP(신호 끊김) 이벤트로 추정"이라고 공유했었는데, **틀렸습니다.** GFW API를 실제로 재조회해서 확인한 결과 이 이상치들은 GAP이 아니라 **port_visit(항구 정박) 이벤트의 장기 오탐**이었습니다(eventId·duration이 원본과 정확히 일치하는 3건 표본 전부 `type="port_visit"` 확인됨). 항구 근처에서 AIS 신호가 뜸해지는 구간을 GFW 알고리즘이 하나의 정박으로 뭉쳐버린 것으로 보입니다.

**score팀 확인 필요**: `axis_a_pressure.py` 등에서 `durationHours`를 쓰는 로직이 있다면, 이 이상치(최장 14년짜리 값 포함)가 정규화·백분위 계산을 왜곡시키지 않는지 확인해주세요.

## 5. 연안AIS 통계 API — 막힘

- data.go.kr 사용 신청(개발계정)은 자동 승인됨
- 그런데 실제 서버는 신청 사이트(`apis.data.go.kr`)가 아니라 **별도 서버(`gicoms.go.kr`, 해사안전관리과 자체 운영)** — 해양기상 API와 똑같은 패턴
- 그 서버에 키를 보내면 "등록되지 않은 인증키"라고 거부됨 — GICOMS 쪽에 별도 등록이 더 필요한 것으로 보임
- 요청 방식·응답 형식은 실제 가이드 문서로 이미 확인해서 코드까지 만들어뒀음(`data/ais_stats_client.py`) — **키 문제만 풀리면 바로 쓸 수 있음**
- 문의처: 해사안전관리과 044-200-5691~2

## 6. 지금 팀원별로 가능한 작업

### 막힌 것 정리

**완전히 막힌 작업은 없습니다.** 대부분 필요한 자료가 이미 준비돼 있어서 진행 가능합니다. 정확도에 영향을 주는 건 아래 2가지뿐이고, 둘 다 제가 혼자 정할 수 없는 팀 판단 사항입니다:

| 항목 | 영향받는 작업 | 필요한 것 |
|---|---|---|
| 어업종 매핑 확정 | `axis_b_baseline.py`의 어업 종류 관련 계산 정확도 | 초안 완성됨 → 팀 회의에서 애매한 8개·대응 안 되는 2개 확정 |
| GFW 오분류 대응 방침 | score에서 쓸 어업선박 목록(31,605척) 자체 | 663척 중 600척이 비어선인 것 발견(3번 참고) → 그대로 쓸지 걸러낼지 팀 결정 |

연안AIS 키·기관출력 단위는 외부 기관 응답을 기다리는 중이지만, **지금 이것 때문에 막혀있는 팀원 작업은 없습니다**.

| 담당 | 작업 | 상태 |
|---|---|---|
| 최지희 | `app.py`/`map/` | 가능 — `data/mock/` 샘플로 화면 작업 가능 |
| 김준기·오동규 | `axis_a_pressure.py`(A축) | 가능 — GFW 이벤트 데이터만 있으면 됨 |
| 김준기·오동규 | `axis_b_physics.py`(B축 물리식) | 부분 가능 — 톤수 아는 선박(535척)만 |
| 김준기·오동규 | `axis_b_baseline.py`(B축 LightGBM) | **이제 재료 다 준비됨** — 해양기상 부착 완료, 어업종 매핑은 초안으로 우선 대입 가능 |
| 김준기·오동규 | `chain/` | 착수 전 — score 결과물 나와야 시작 가능 |

## 6-1. 다음 방향

지금은 데이터 수집 쪽에서 더 할 게 없는 단계입니다. 다음 사이클은 이렇게 갑니다:

**score팀 계산(민감도 확인) → 데이터 수집 피드백(뭐가 영향 있는지) → 데이터 수집 개선(그 부분만)**

즉 무작정 데이터를 더 모으는 게 아니라, score 결과가 실제로 흔들리는 부분이 확인되면 그때 그 부분만 정밀하게 개선하는 방향입니다.
