# 개인 작업 노트 (담당: 김태윤 — 개인 참고용)

`data/` 작업 중에 겪은 실수/노하우를 기록해두는 문서. GFW에 국한되지
않는 일반적인 것들(도구 사용법, 흔한 함정 등)을 담는다. GFW API 자체의
동작 방식은 `data/gfw_collection_notes.md`에 따로 있다.

**스코프**: 이것도 개인 참고용이다 — 다른 담당자 코드나 작업 방식에
영향 주지 않는다. 프로젝트 공식 규칙(구속력 있음)은 `rules_common.md`,
`rules_gfw.md`를 본다 — 여긴 그 규칙들을 지키는 과정에서 겪은 사고/삽질
기록일 뿐이다.

## Windows 콘솔에서 한글 출력을 눈으로 믿지 말 것

**증상**: `python -c "..."`나 스크립트의 `print()` 결과를 Windows 터미널로
보면 한글이 깨져서(`????` 같은 mojibake) 나온다. 이걸 보고 "데이터가
깨졌나?"라고 오해하기 쉽다.

**실제 원인 사례(2026-08-14)**: 국내 선박제원정보 API의 `vesselKind` 값을
확인하다가, 콘솔에 깨져 보이는 걸 "어업 어선"으로 잘못 읽고 매칭 규칙에
`"어업"`이라는 키워드를 넣었다. 실제 값은 `"92[원양 어선]"`이었고
"어업"이라는 단어는 아예 없어서 규칙이 계속 실패했다. 처음엔 인코딩
버그로 의심해서 raw 파일 바이트까지 파봤는데, **파일 자체는 처음부터
멀쩡했다** — 콘솔 출력만 깨져 보였던 것뿐.

**교훈**: 한글 값이 기대한 대로인지 확인해야 할 때는 `print()`로 눈으로
보고 판단하지 말고:
1. `repr()`이나 `[hex(ord(ch)) for ch in s]`로 코드포인트를 직접 찍어서
   비교하거나,
2. 결과를 파일로 저장한 뒤 Read 도구로 확인한다 (Read는 콘솔 코드페이지
   문제 없이 정확하게 보여줌).
3. 소스 코드에 한글 리터럴을 직접 타이핑하는 대신 `chr(0x....)`처럼
   코드포인트로 쓰면, 소스 파일 인코딩/셸 인자 전달 과정에서 깨질 여지
   자체를 없앨 수 있다 (디버깅할 때 특히 유용).

`python -c "..."`로 한글을 셸 인자에 직접 넘기는 것도 피하는 게 안전하다
— 별도 `.py` 파일로 작성해서 실행하는 편이 낫다(그래도 콘솔 print 출력
자체는 깨질 수 있으니 위 1~2번 방법과 같이 써야 한다).

**추가(2026-08-14)**: 한글이 섞인 `print()`를 하는 스크립트, 특히
백그라운드로 오래 돌리는 스크립트는 맨 위에 아래를 꼭 넣는다 — 안 넣으면
콘솔이 표시만 깨지는 게 아니라 **`UnicodeEncodeError`로 스크립트 자체가
죽는다.** 실제로 겪은 사례: 9,468척 수집이 82% 진행된 시점에 "API 에러
20회 연속" 경고 메시지를 출력하려다(그 메시지 안에 "—" 문자가 있었음)
그 print() 자체가 크래시를 일으켜서, 정작 왜 에러가 났는지 로그도 못
남기고 백그라운드 프로세스가 조용히 죽었다. 예전에 만들어둔 다른
검증 스크립트에는 이미 이 방어 코드가 있었는데 새 스크립트에 처음부터
안 넣어서 겪은 문제 — 앞으로는 무조건 첫 줄에 넣는다.

```python
if hasattr(sys.stdout, "reconfigure"):
    sys.stdout.reconfigure(encoding="utf-8")
    sys.stderr.reconfigure(encoding="utf-8")
```

## 반복 API 호출 스크립트는 처음부터 병렬로 짤 것

**규칙**: 같은 작업을 항목 단위로 여러 번 반복하는 스크립트(API 호출 등)를
짤 때는:
1. 항목들이 서로 독립적이면(이전 결과에 의존 안 하면) 처음부터 병렬
   처리(예: `ThreadPoolExecutor`)로 짠다 — 순차로 짜고 나중에 고치지
   않는다.
2. 전체를 돌리기 전에 10~30건 정도로 먼저 실행해서 건당 처리 시간을
   재고, 전체 건수로 환산해 예상 총 소요시간을 계산한다.
3. 예상 소요시간이 길면(기준: 30분 이상) 실행 전에 먼저 알리고 진행
   여부를 확인한다. 짧으면 바로 진행한다.
4. 결과는 파일로 저장하고, 화면에는 요약 로그(진행률, 건수)만 남긴다 —
   전체 데이터를 콘솔에 출력해서 보지 않는다(토큰 낭비 방지, 이미
   확인된 원칙).

**이유**: 국내 선박제원정보 9,468척을 순차 처리로 돌렸다가 16분에
323건 처리되는 걸 보고서야 "이 속도면 7~8시간 걸린다"는 걸 뒤늦게
발견했음(2026-08-14). 처음부터 소규모로 시간을 재고 병렬화했으면
안 겪었을 문제.
