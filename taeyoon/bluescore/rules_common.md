# BlueScore 데이터 수집 — 공통 규칙

이 문서는 BlueScore 프로젝트에서 **어떤 외부 데이터 소스(GFW API, 국내
공공데이터포털 등)를 수집하든 공통으로 적용되는 규칙**을 담는다.

특정 소스만의 고유 규칙(엔드포인트, 파라미터 문법, 데이터셋 이름 등)은
`docs/rules_gfw.md`처럼 소스별 문서에 따로 담고, 이 문서를 참조하게
한다.

---

## 1. 최상위 원칙

**수집과 가공을 절대 섞지 않는다.**

```
1단계: API 호출 → 응답을 가공 없이 그대로 저장     ← 모든 수집 코드가 여기까지만
2단계: 저장된 raw 데이터를 표로 펴기(평탄화)         ← 별도 규칙
3단계: 필터링, 분류, 판단 등 실제 가공              ← 별도 규칙
```

값을 읽고 판단하는 로직이 들어가는 순간 수집 코드의 책임 범위를
벗어난 것이다. "이거 필터링 아닌가?"라는 의심이 드는 순간 멈추고
재확인한다.

**이 원칙은 개인정보 배제보다 우선한다.** 응답에 개인정보 가능성이
있는 필드(예: 소유자명)가 포함돼 있어도, 수집 단계에서는 걸러내지
않고 원본 그대로 저장한다. 개인정보를 빼는 것도 하나의 "판단"이므로
필터링 단계의 책임이다. 다만 그런 필드가 존재하는지, 몇 건인지는
참고용 로그로 남겨 다음 단계 담당자가 알 수 있게 한다.

---

## 2. 저장 규칙

**형식: 원문 그대로.** 응답을 파싱해서 재직렬화하지 않는다. 원본이
JSON이면 JSON 텍스트 그대로, 다른 형식이면 그 형식 그대로 저장한다.
가공 없이 보존하는 게 원본 구조(중첩, 리스트, null vs 빈 문자열
같은 미묘한 차이)를 잃지 않는 유일한 방법이다.

**스냅샷 원칙: 재조회해도 기존 파일을 덮어쓰지 않는다.**

이유: 외부 API의 데이터는 소스에 따라 갱신 지연이 있을 수 있다(GFW
registry는 최대 2개월 지연 등, 소스별 상세는 각 소스 문서 참고).
"이 시점에 실제로 어떤 값이었는지"를 나중에 재현하려면, 새로 받은
데이터가 예전 데이터를 지워버리면 안 된다.

파일명에 조회 시각을 붙여서 스냅샷을 구분한다. 같은 시각에 재호출
되어 이름이 겹치면 접미사를 붙여서라도 절대 덮어쓰지 않는다.

**저장 단위(폴더 등)를 응답 종류별로 분리한다.**

이유: 서로 다른 종류의 응답은 "무엇으로 식별되는가"가 다르다. 예를
들어 검색 결과는 쿼리 조건이 정체성이고, 상세 조회는 개별 ID가
정체성이다. 한곳에 섞으면 다음 단계(평탄화)에서 "이 묶음은 통째로
이 함수에 넣으면 된다"는 단순한 대응이 깨진다.

**메타데이터는 응답 본문과 분리해서 남긴다.**

요청 URL, 파라미터, 상태코드, 응답시간, 조회 시각 등은 응답 본문과
별도로 기록한다. 본문에는 절대 섞지 않는다 — 원본 오염 방지가 목적이다.

**소스별로 저장 경로를 분리한다.**

```
raw_data/
├── gfw/
├── domestic/
└── (새 소스)/
```

한 프로젝트 안에 여러 소스가 쌓이므로, 소스가 섞이지 않도록 최상위
경로부터 나눈다.

## 3. 재시도 / 실패 처리 규칙

**재시도 대상:** 429, 500, 502, 503, 524
**재시도 정책:** 최대 3회, 대기 간격 2초 → 4초 → 8초 (지수 백오프)
**재시도하지 않는 것:** 401 등 인증/요청 자체가 잘못된 경우 — 재시도
해도 같은 결과이므로 즉시 실패 처리하고 다음으로 넘어간다.

**한 건의 실패가 전체를 멈추지 않는다.** 예를 들어 300건 중 5번째
항목 조회가 3회 재시도 후에도 실패하면, 그 항목은 실패로 기록하고
6번째로 넘어간다. 전체 수집이 중단되지 않는다.

이 정책은 기본값이다. 특정 소스가 별도의 제약(예: 동시 요청 수 제한)
을 갖고 있으면 그 소스의 문서에 추가로 기록한다.

---

## 4. 인증 규칙

토큰/API 키를 코드에 하드코딩하지 않는다. `.env` 파일에서 읽되, 이
파일은 반드시 `.gitignore`에 포함해 저장소에 커밋되지 않도록 한다.

우선순위: 환경변수가 이미 설정돼 있으면 그것을 쓰고, 없으면 `.env`
파일에서 읽는다.

여러 소스의 키를 한 `.env` 파일에서 관리한다:
```
GFW_API_TOKEN=...
DATA_GO_KR_API_KEY=...
```

## 5. 조회 기간 — 반기 단위 규칙

시간 범위가 필요한 수집(예: 이벤트, 활동 기록)에는 아래 반기 규칙을
공통으로 적용한다.

**고정 반기 구간:** 1/1~6/30 (H1), 7/1~12/31 (H2)

**추출 범위 계산 규칙:**
```
추출 범위 = [직전 완결 반기의 시작일] ~ [오늘]
```

오늘이 속한 반기가 아직 안 끝났으면, 그 미완결분을 버리지 않고
직전 완결 반기와 합쳐서 하나의 연속 구간으로 추출한다.

**예시 (오늘 = 2026-08-13):**
```
오늘은 2026 H2(7/1~12/31) 안에 있지만 아직 안 끝남
직전 완결 반기 = 2026 H1(1/1~6/30)
→ 추출 범위 = 2026-01-01 ~ 2026-08-13
```

이때 이전 실행과 겹치는 구간이 생길 수 있는데, 겹침을 코드로 미리
배제하지 않는다. 배제 자체가 판단이고, 수집 단계는 판단하지 않는다.
저장 규칙(2번)의 스냅샷 원칙으로 자연스럽게 처리된다.

날짜를 코드에 하드코딩하지 말고, 실행 시점("오늘")을 기준으로 매번
자동 계산한다.

---

## 6. 진행 상태 기록 (중단 후 재개)

수집 도중 네트워크가 끊기거나 강제 종료돼도, 다시 실행하면 이어서
진행할 수 있어야 한다. 이미 완료된 항목은 건너뛰고 남은 것만 처리한다.

단, 조회 기간이 지난 실행과 다르면(예: 반기가 바뀌어 확장 실행하는
경우) 조용히 이어받지 않고 새로 시작한다 — 서로 다른 기간의 진행
상태가 뒤섞이면 안 된다.

매번 처음부터 전체를 다시 수집하는 구조는 이 규칙 위반이다.

---

## 7. 검증 규칙 (수집 후 자동 점검)

수집이 끝나면 아래를 자동으로 점검한다. 하나라도 위반되면 명확히
실패로 표시하고, 이 실행분의 raw 데이터를 다음 단계로 넘기지 않는다.

**모든 소스 공통 하드 게이트:**
1. 저장된 데이터가 원본 구조 그대로인가 (일부 필드만 남긴 흔적 없는가)
2. 검색/목록 조회로 나온 전체 항목 수와 실제 상세조회를 시도한 항목
   수가 일치하는가. 불일치가 있다면 그 항목들이 실패로 기록되어 사유가
   설명 가능한지 확인한다 (이유 없이 조용히 누락되면 위반).
3. 재조회 시 기존 스냅샷 파일이 삭제·덮어쓰기 되지 않았는가
4. 토큰/인증 정보가 저장된 데이터 파일 어디에도 노출되지 않았는가
   (본문뿐 아니라 메타데이터 파일도 포함)

**정보성 체크 (통과/실패 판정 없음, 참고 로그만):**
- 개인정보 가능성이 있는 필드가 몇 건 포함됐는지

소스별로 추가 게이트가 필요하면 각 소스 문서에 덧붙인다.

**게이트가 위반을 잡았을 때, 게이트 자체를 완화해서 통과시키지
않는다.** 원인이 된 실제 코드를 고친다. 예외적으로 원칙 자체를
재조정해야 할 상황이면, 그 판단과 이유를 문서에 명시적으로 기록하고
규칙을 개정한다 — 말없이 코드만 바꾸지 않는다.

## 8. 새 소스를 추가할 때

1. `docs/rules_{소스명}.md` 문서를 새로 만들고, 이 공통 문서를
   참조하게 한다 (예: "재시도/저장 규칙은 `rules_common.md` 참고").
2. 그 소스만의 고유 규칙(엔드포인트, 파라미터 문법, 데이터셋 이름,
   소스별 지연시간, 소스별 추가 게이트 등)만 소스 문서에 적는다.
3. 코드에서 공통 로직(재시도, 원문 저장)은 기존 공통 모듈을 재사용
   하고, 소스 고유 로직만 새로 짠다. 완전히 새로운 코드를 처음부터
   다시 짜지 않는다.
4. **파라미터 문법 등 문서만으로 확정되지 않는 부분은, 코드를 다 짜기
   전에 소규모로 실제 호출해서 먼저 확정한다.** 확정 안 된 채 대량
   수집을 시작하지 않는다.

5. **문법 확정 단계에서 토큰(비용)을 절약하는 방법:**
   - 문서(특히 JS로 렌더링되는 API 문서 사이트)를 웹에서 여러 번 재조회
     하기보다, **실제 API에 최소 비용(작은 limit)으로 sanity call을
     먼저 던져 확인하는 쪽이 더 빠르고 싸다.** 문서 페이지는 요약 도구를
     거치면서 실제 예시 코드나 파라미터 제약(허용 범위, 필수 여부 등)이
     누락되기 쉽다 — 반면 API가 돌려주는 4xx 에러 메시지에는 그 정보가
     그대로 들어있는 경우가 많다.
   - 확인할 조합이 여러 개면(예: 파라미터명 A/B × 따옴표 종류 2가지),
     전부를 무작정 다 시도하지 않는다. 문서/사례로 봤을 때 가장 유력한
     조합 하나를 먼저 시도하고, 그 결과(성공/실패, 에러 메시지)를 보고
     다음에 무엇을 좁혀서 시도할지 정한다.
   - 200 응답이 왔다고 끝난 게 아니다. **응답 바디를 실제로 열어서
     의도한 필터/조건이 적용됐는지 확인한다.** (예: 200이지만 조건이
     자유 텍스트로 처리되어 엉뚱한 결과가 섞여 나오는 경우가 있음 —
     상태 코드만으로 문법이 맞다고 판단하지 않는다.)
   - 4xx 에러 메시지(400, 422 등)를 무시하지 않는다. 파라미터명이나
     허용 범위(예: "limit must not be greater than 50", "property
     offset should not exist")처럼 다음 시도를 바로 좁혀주는 정보가
     들어있는 경우가 많다.
   - 페이지네이션 방식(offset 기반인지, 커서/토큰 기반인지)도 문서로
     추측하지 말고 위와 같은 방식으로 실제 호출 1~2회로 확정한다 —
     대량 수집 코드를 다 짜고 나서 방식이 틀렸다는 걸 알게 되면 그
     비용이 훨씬 크다.

## 9. 이 규칙을 어긴 것으로 간주되는 사례 (체크리스트)

코드 작성/리뷰 시 아래에 해당하면 규칙 위반이다.

- [ ] 응답을 받은 즉시 파싱해서 필요한 값만 뽑고 원본을 버림
- [ ] 특정 조건으로 일부 항목을 수집 대상에서 제외
- [ ] 재조회 시 기존 파일을 덮어씀
- [ ] 서로 다른 종류의 응답을 구분 없이 한곳에 저장
- [ ] 하나의 요청 실패로 전체 수집 프로세스가 종료됨
- [ ] 토큰이 코드 파일 안에 문자열로 박혀 있음
- [ ] 조회 기간을 코드에 고정값으로 박아넣음
- [ ] 소스 고유 문법을 확인 없이 추측만으로 코드에 반영함
- [ ] 하드 게이트가 실패했을 때 게이트를 느슨하게 고쳐서 통과시킴
- [ ] 새 소스 코드를 짤 때 기존 공통 모듈을 안 쓰고 처음부터 복붙해서 새로 짬
