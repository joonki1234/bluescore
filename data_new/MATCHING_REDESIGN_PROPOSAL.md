# GFW↔국내등록 선박 매칭 재설계 검토 (2026-08-18, 김태윤)

상태: **팀 결정 대기**. 로마자 유사도 매칭을 한글 직접비교로 바꾸면 정밀도가
얼마나 오르고 대신 뭘 잃는지 정리한 자료. 반영 여부는 팀 결정 필요.

## 배경

현재 라이브에 커밋된 매칭(`data_new/process/assemble_matches.py`,
`FUZZY_NAME_THRESHOLD=0.8`)은 GFW 자기신고 영문명을 로마자로 변환해 국내
등록명(TAC·어선원부)과 문자열 유사도로 비교한다. 사람 라벨링 80쌍 검증에서
**정밀도 약 75%**로 이미 팀 결정에 반영돼 있다(CLAUDE.md 10번).

이번에 GFW 영문명 4,662척 전체를 사람이 직접 한글로 재변환한 데이터
(`data_new/gfw_korean_name_candidates.csv`, 3,878척 채워짐, 이미 커밋됨)가
생겨서 — 로마자 대신 한글 원문끼리 직접 비교가 가능해졌다. 그 결과를 검증한
요약이다.

## 발견한 것 3가지

**1. 숫자접두어 필터가 근거는 있는데 코드엔 없음**
PROCESS_LOG 49번에서 "번호 일치 시 정밀도 95~100%, 불일치 시 0%"가
검증됐고 CLAUDE.md가 이 근거로 0.8 임계값을 확정했는데, 정작
`assemble_matches.py`의 `_total_score`엔 반영돼 있지 않다
(nameScore+tonnageBonus+locationBonus뿐, numericBonus 없음).

**2. 로마자 유사도의 구조적 오탐("-성호" 문제)**
서로 다른 실제 이름인데 로마자로 바꾸면 끝부분이 겹쳐서 유사도 점수가
높게 나오는 사례가 실측됨.
```
EUNSEONGHO(실제: 은성호) → 로마자매칭 결과: 금성호(GEUMSEONGHO)로 오매칭
DEOG YANG HO(실제: 덕양호) → 로마자매칭 결과: 동양호로 오매칭(verified 처리됨, nameScore 0.9)
```

**3. 한글 exact-match는 신뢰도 높지만, fuzzy는 위험**
한글 직접비교로 exact match된 916척은 구조적으로 신뢰도 높음. 반면
fuzzy(0.85+) 허용 시 "제N호"류(선단 일련번호) 이름에서 내부 숫자가 변환
과정에 빠지는 버그로 검증 사례 19건 전부가 오매칭 — fuzzy는 폐기 결정.
```
JE1JOYANGHO  → 제7조양호
JE8JOYANGHO  → 제7조양호   (다른 두 GFW가 같은 배 주장, 최소 하나는 오답)
```

## 결과 비교 — 기존 vs 신규(exact-only)

| | 기존(현재 라이브) | 신규(한글 exact-only) |
|---|---|---|
| matched/verified | 2,881척(54.1%) | 916척(17.2%) |
| 정밀도 | ~75%(사람검증) | ~98%+(구조적 추정, 사람검증 0건) |
| 추정 진짜정답 | ≈2,161척 | ≈900척 |
| 추정 오탐 | ≈720척 | 거의 0 |
| +held(낮은신뢰도, 계산가능) | (구조 없음) | +535척 → 27.3%까지 |
| unmatched 취급 | 2,442척 | 3,211~3,747척 |

정밀도 vs 커버리지 트레이드오프다. 오탐 하나가 B축(효율) 점수를 그 배
단위로 완전히 틀어지게 만들 수 있어, 어느 쪽을 우선할지는 코드가 아니라
정책 판단이다.

## held(모호 매칭) 세부 구성 — 5,323척 전체

| 구분 | 척수 | 비중 | 비고 |
|---|---:|---:|---|
| verified(한글 exact) — 사용 권장 | 916 | 17.2% | 단일후보 또는 동률→최근접 확정(≤50km) |
| held·위치애매(50~150km) — 사용 가능 | 535 | 10.1% | 후보 1개, 거리만 불확실 |
| held_multi·진짜 동명이선 — 계산 불가 | 838 | 15.7% | 실제 다른 배 여러 척, 톤수 차 최대 20배 |
| held_multi·버그(내부번호) — 재작업 필요 | 17 | 0.3% | "제N호" 변환 시 번호 소실 |
| held_multi·원인불명 — 재검토 | 65 | 1.2% | 느슨한 fuzzy(0.85) 탓 의심 |
| held·로마자 fallback — 계산 비권장 | 65 | 1.2% | 한글후보 없는 784척 중 일부, 표본 검사서 오탐 다수 |
| unmatched(후보 없음) | 2,226 | 41.8% | 변환추측 실패 또는 실제 미등록 |
| no_name(GFW 이름 자체 없음) | 661 | 12.4% | 기존과 동일, 손댈 수 없음 |

## 선택지

**A. 현행 유지** (작업량 없음)
커버리지 54.1% / 정밀도 ~75%(오탐 약 720척 포함 추정). 아무것도 안 바꿈.

**B. 숫자필터만 추가** (작음 — 한 줄 수준)
이미 팀이 인용한 근거(PROCESS_LOG 49번)를 코드에 실제로 반영. 위험 적음,
즉시 가능. 정확한 개선폭은 재실행 후 확인 필요.

**C. 한글비교로 전체 교체** (중간 — 시뮬레이션 코드 포팅)
verified 916척(정밀도 최상) + held 535척(계산 가능, 낮은신뢰도) = 27.3%
커버리지. 스키마 호환이라 B축 소비 코드(`score/real_axis_b_input.py`)는
안 건드려도 됨(`tac`/`mof` 객체 존재 여부만 읽지 `matchTier` 값은 안 봄,
실측 확인함). 단 "0.8 임계값 재론 불필요"로 못박은 팀 결정을 사실상
뒤집는 변경.

## 팀 결정 필요

1. **A/B/C 중 방향** — 마감 압박 감안해서 지금 시점에 반영할지, 이번
   제출은 현행 유지하고 다음으로 미룰지
2. **(C 선택 시) held 535척 처리** — 낮은신뢰도로 점수 노출할지,
   unmatched처럼 블록할지(`ui/adapter.py`의 `matchingFailed` 게이팅과 연결)
3. **버그 3건(17+65척)** — "제N호" 변환 로직 재작업 필요 여부, 급하지
   않으면 다음 라운드로
