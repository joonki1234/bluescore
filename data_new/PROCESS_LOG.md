## 1. 도메인 지식 정리 — 재확인 필요 항목

| 항목 | 가설/이전 결론 | 재확인 필요 이유 |
|---|---|---|
| TAC↔GFW 식별자 | 공통 키 없는 별개 체계(어선번호 vs MMSI/콜사인/IMO) | 공식 대조표 유무 미확인 |
| 국내↔GFW 어법 분류 | 해상도 차이(국내 세분화 vs GFW 대분류) — 다대일 관계 | 이번 실데이터로 매핑 재설계 |
| GFW 이벤트 5종 | AIS 궤적 기반 추론, 직접 관측 아님 | 오탐률 재검증 대상 |
| AIS 속도 | 대지속도(대수속도 아님) — 유속 강한 해역에서 연료추정 왜곡 가능 | 보정 여부 미정 |
| "자원압력" 지표 | CPUE 대체재 아니라 "조업노력 집중도"에 가까움 | 성어기 혼동 위험, season_key로 일부 통제 |

## 4. 수집 원칙(방법론) 설계 — 결정 사항

(진행 중 — 판단 확정되는 대로 표로 채운다)

| 항목 | 결정 | 근거 |
|---|---|---|
| 원본 저장 방식 | API 응답 그대로 저장(가공 없이) | 저장 시점에 판단 로직을 넣으면, 그 판단이 나중에 틀린 것으로 밝혀졌을 때 재현 불가능(API 갱신 등)해서 재수집해야 함. 원본 보존 시 가공 로직만 다시 돌리면 됨 — 실수 복구 비용 차이 |
| 재조회 시 덮어쓰기 여부 | 기본은 스냅샷(덮어쓰지 않음) — 단, 소스별로 "순수 추가형"인지 sanity call(4번 단계)에서 실측 확인 후 예외 허용 | 순수 추가형이면 덮어써도 손해 없지만, 값이 정정·재분류될 수도 있어(예: 톤수 정정, 이벤트 재분류) 미리 다 안전하다고 가정하면 안 됨. 확인 전까지는 안전한 쪽(스냅샷) |
| 재시도 정책 | 일시적 에러(429/500/502/503)는 대기시간 늘려가며 재시도(2초→4초→8초, 최대 3회). 요청 자체 오류(400/401)는 재시도 안 함 | 일시적 에러는 서버가 잠깐 바빴을 뿐이라 재시도로 해결될 확률 높음. 요청 오류는 같은 요청 다시 보내도 같은 이유로 또 실패 — 재시도가 시간 낭비 |
| 실패 처리 범위 | 항목 하나 실패해도 전체 수집은 계속 진행, 실패 항목만 기록 | 전체를 중단하면 이미 받은 데이터도 못 쓰고 처음부터 다시 해야 함 |
| 중단 후 재개 | 진행상태를 기록해두고 재실행 시 이어서 진행. 단, 수집 조건(기간·대상 등)이 지난 실행과 다르면 이어받지 않고 새로 시작 | 이어받기는 시간·API 호출횟수 낭비를 줄임. 조건이 다른데 이어받으면 일부 구간이 조용히 누락될 수 있어 조건 일치를 전제로 함 |
| 인증키 관리 | 코드에 하드코딩 안 함, `.env`에서 읽고 `.gitignore`에 포함 | 코드 파일은 git으로 공유·관리되고, 한 번 커밋되면 나중에 지워도 git 히스토리에 영구히 남음 |
| 저장 폴더 구조 | 소스별로 최상위 폴더 분리(`raw/gfw/`, `raw/vessel_spec/` 등) | 소스마다 응답 구조·갱신 주기·읽는 로더가 다름. 한 폴더에 섞으면 "이 폴더 통째로 읽으면 된다"는 단순한 로더 설계가 깨짐 |
| 메타데이터 분리 | 요청 파라미터만 본문과 별도 기록. 조회시각(스냅샷 파일명으로 이미 커버)·상태코드·응답시간은 필수 아님 | 나중에 "이 항목이 왜 결과에 없지" 확인하려면 그때 어떤 조건으로 조회했는지 알아야 함 — 본문만으론 안 보임. 나머지는 진단에 편리한 정도라 필수로 안 둠 |
| 검증 게이트 — 건수 일치 | 목록 API의 total과 실제 저장 건수를 자동 비교, 불일치 시 실패 표시 | 페이지네이션 도중 조용히 끊겨도 알아채기 어려움 — 건수 비교로 잡아냄 |
| 검증 게이트 — 원본 구조 보존 | 저장된 응답이 원본 구조 그대로인지(일부 필드만 남은 흔적 없는지) 확인 | "가공 없이 저장" 원칙이 실제 코드에서 지켜졌는지 자동 점검 |
| 검증 게이트 — 스냅샷 보존 | 재조회 시 기존 스냅샷 파일이 삭제·덮어쓰기 안 됐는지 확인 | "덮어쓰지 않기" 원칙이 실제로 지켜졌는지 자동 점검 |
| 검증 게이트 — 인증키 비노출 | 저장된 파일(본문·메타데이터 모두) 어디에도 토큰값이 없는지 확인 | 헤더 로깅 실수 등으로 키가 파일에 찍히는 사고 방지 |
| 조회 기간 관리 | 코드에 고정값으로 박아넣지 않고 실행 시 파라미터로 지정 | 인증키와 같은 논리 — 다른 기간으로 다시 돌리려면 코드를 고쳐야 하는 구조를 피함 |
| 스냅샷 읽기 방식 | 스냅샷을 읽는 코드는 특정 파일명을 고정하지 않고 항상 최신 파일을 자동으로 찾음 | "덮어쓰지 않기" 원칙의 직접적 후속 문제 — 특정 파일명을 고정하면 새 스냅샷이 쌓여도 계속 옛 파일을 읽게 됨. 에러 없이 조용히 stale해져서 알아채기 어려움 |
| 개인정보 가능 필드 | 원본 그대로 저장(원칙1과 일치)하되, 포함 건수는 로그로 남겨 가공 담당자가 알 수 있게 함 | 저장 단계에서 거르는 것도 하나의 판단이라 수집 책임 범위 밖 — 다만 존재 여부는 후속 단계가 알아야 함 |
| 출처 신뢰도 우선순위 | ① 실제 API 라이브 호출(sanity call) ② 공식 소스코드(예: 공식 클라이언트 라이브러리 원본) ③ 1차 공식 문서(활용가이드 PDF 등) ④ 공식 문서 웹페이지 ⑤ 검색엔진 요약. 기억·추정은 검증 전까지 근거로 안 씀 | GFW 문서 사이트가 JS 렌더링이라 웹 요약만으론 부정확했고, 실제로는 공식 파이썬 클라이언트 소스코드(②)에서 훨씬 정확한 정보(Events가 POST라는 점 등)를 얻음. 기억으로 짠 GFW 호출 문법(where/limit)도 나중에 실제 호출(①)로 재검증하고 나서야 확정으로 인정함 |

## 5. GFW 소스 이해 — sanity call + 공식 소스코드 확인 결과

| 확인 항목 | 결과 | 확인 방법 |
|---|---|---|
| Vessels Search 문법 | `where`(SQL형 다중조건)/`query`(단일 식별자), `datasets`는 `public-global-vessel-identity:latest`만 유효, `limit` 기본 20·최대 50 | 실제 호출(422 에러 메시지) + 공식 파이썬 클라이언트 소스코드(`VesselSearchParams`) 이중 확인 |
| Vessels Search 페이지네이션 | `since` 커서 토큰 방식 | 실제 호출 |
| Events 호출 방식 | **POST**(`events` 경로), body에 필터조건(datasets/vessels/types/start_date/end_date 등), 쿼리파라미터는 limit(기본 99999)/offset/sort | 공식 클라이언트 소스코드(`EventListEndPoint`가 `PostEndPoint` 상속) — 기억(GET이라 알고 있었음)과 다름, 정정됨 |
| 이벤트 타입 | 6종: ENCOUNTER/FISHING/GAP/GAP_START/LOITERING/PORT/PORT_VISIT | 공식 소스코드(`EventType` enum) — "5종"이라는 기억과 다름, 정정됨 |
| 이벤트 원본 구조 | vesselId/latitude/longitude/averageSpeedKnots/durationHours 같은 flat 필드는 원본에 없음. `vessel.id`, `position.lat/lon`, 타입별 하위객체(`fishing.*`, `gap.*`, `port_visit.*`)에 중첩돼 있음 | 공식 소스코드(`EventItem` 응답 모델) — score/ 계약 필드와 원본 구조가 다르다는 것 발견, `SCHEMA_DRAFT.md`에 정규화 필요 사항으로 반영 |
| KOR 국적 선박 모집단 성격 | `flag='KOR'`만 걸면 90%+ 비어업 대형선(화물선 등). `shiptype=FISHING` 필터링해도 21.7%가 원양(RFMO 등록) 선단, 14%가량 자체 오염(비어업 어구 등록) | 실제 페이지네이션 실측(2000건+ 표본) |
| `registryInfo.geartypes` 신호 | 국제기구(RFMO) 등록 선박에만 주로 채워짐(68.7%가 공란) — 국내 근해·연안 다수엔 없어 일반화 못 함 | 실측 표본 |
| GFW 자체 마력(엔진출력) 데이터 | 리서치 페이지는 "추론 모델 있음"이라 홍보하지만, 실제 API 응답(JSON)엔 노출 안 됨 | 실제 호출 응답 전체 키 스캔 |
| **국적(flag=KOR)과 실제 조업 위치는 무관함(결정적 발견)** | `MEDRA`(flag=KOR, TRAWLERS/FISHING) 실제 조업이벤트 위치가 서아프리카(기니비사우 인근, `eez:"8472"`, FAO "34")였음. 한국 국적이라고 한국 근해에서 조업한다는 보장이 전혀 없음 | Events API(POST) 실제 이벤트 좌표·`regions.eez` 확인 |

### 모집단 정의 방향 전환 (확정)

국적(flag) 기준이 아니라 **이벤트 발생 위치(한국 EEZ 안에서 실제로 조업했는가)**로
"근해" 모집단을 정의하기로 결정 — 국적·선종·RFMO등록 여부를 조합해 간접 추정하는
것보다, 실제 조업 위치라는 직접적 사실 하나가 더 결정적이고 단순함.

**실측 검증 완료(2026-08-17)**: Events API POST body에
`region: {"dataset": "public-eez-areas", "id": "8327"}`(한국 EEZ, marineregions.org
MRGID) + `flags: ["KOR"]`을 걸어 실제 호출한 결과, 반환된 선박명이 ANNA/HAE JOON/
DAE SEUNG HO/202 HEUNG SEONG HO 등 국내 어선 특유의 "OO호" 작명 패턴 — 앞서
`flag='KOR'` 단독 필터에서 나왔던 동원/오룡 등 대형 원양선단과는 확연히 다른
모집단임을 확인함. `public-eez-areas` 데이터셋명과 `8327`(marineregions.org
검색으로 찾은 값)은 둘 다 이번 실제 호출 성공으로 검증됨 — 문서 추측이 아니라
실측 확정.

**모집단 후보 정의(6번 단계에서 최종 확정 예정)**: `flag='KOR'` AND 조업이벤트가
`region.eez=8327`(한국 EEZ) 내에서 1건 이상 발생. 국적만으로 거르지 않고, 실제
조업 위치라는 사실 기반으로 "근해" 여부를 판정 — 이번 재구축의 핵심 개선점.

### 5개 이벤트 타입 실측 확인 (한국 EEZ, KOR국적, 2025-01~2026-08 표본)

| 타입 | total | 실측 발견 |
|---|---:|---|
| FISHING | (별도 표본, 위 참고) | `fishing.averageDurationHours`가 null인 경우 있음(실측 확인) |
| GAP | 0건 | 극희소하다는 이전 관찰과 일치(재확인) |
| ENCOUNTER | 30,607건 | `encounter.vessel`에 상대방 선박 정보 중첩(자기 자신 vessel과 별개) |
| LOITERING | 324,263건 | **장기 이상치 재발견**: 한 이벤트가 `totalTimeHours: 31,918시간`(3.6년), 선박 `type:"other"`(비어선), `averageSpeedKnots: 0.12`(사실상 정지 상태) |
| PORT_VISIT | 1,317,282건 | **장기 이상치 재확인**: `durationHrs: 126,083시간`(14.4년, 2012~2026) — 예전 발견("최장 5,082일=14년")이 이번 신선한 데이터에서도 독립적으로 재현됨. **port_visit만이 아니라 loitering에서도 같은 패턴 발생** — GFW가 장기 저속/정박 구간을 이벤트 하나로 뭉치는 건 특정 데이터의 결함이 아니라 알고리즘의 구조적 특성으로 보임(대응 필요) |

**주의사항 발견**: 응답의 `type` 필드값은 소문자(`fishing`/`encounter`/`loitering`/
`port_visit`)인데, 요청 필터용 `EventType` enum은 대문자(`FISHING` 등) — 정규화
코드에서 대소문자 안 맞추면 조용히 필터링 실패할 수 있음.

확정 후 실제 호출로 검증.

| 확인 항목 | 결과 |
|---|---|
| 엔드포인트 | `http://apis.data.go.kr/1192000/SicsVsslManp3/Info3` (GET, XML), 파라미터 `serviceKey/vsslNm/clsgn/numOfRows/pageNo` |
| `vsslNm` 검색 방식 | **부분일치(포함검색)** — "ANNA" 검색 시 170건("MARIANNA KOSAN", "JOHANNA C", "GIANNA" 등 "ANNA"가 들어간 모든 배 포함). 정확일치 아님 |

### ⚠ 결정적 발견: GFW `selfReportedInfo`의 콜사인/IMO는 신뢰 불가

GFW에서 "SU HAE NO.7"(flag=KOR, 자기신고 어업선박)의 `selfReportedInfo.callsign
=9LU2079`, `imo=8865547`을 그대로 MOF에 조회했더니, MOF는 이 콜사인+IMO를
**전혀 다른 배**로 반환함 — 선명 `POLARIS PRINCE`, 국적 시에라리온,
선박종류 `62[이·접안용 예선]`(예인선, 어선 아님).

이 값이 GFW `registryInfo`(공식 등록부 매칭)가 아니라 `selfReportedInfo`(AIS
자기신고, 검증 안 됨)에서 나온 것이었다는 점이 핵심 — 도메인 지식(3번)에서
짚었던 "AIS 자기신고 필드는 선원 입력 오류·오래된 정적 정보 재사용 등으로
신뢰도 낮다"는 우려가 실제 사례로 확인됨.

**결정(5번 조인키 설계에 반영 예정)**: GFW→MOF 매칭에는 `selfReportedInfo`의
콜사인/IMO를 그대로 쓰지 않는다. `registryInfo`(공식 매칭된 것)만 신뢰 가능한
조인키 후보로 취급 — `registryInfo`가 없는 선박(자기신고만 있는 다수)은 이름
기반 매칭 외 다른 방법이 필요하며, 그 자체가 5번 단계의 핵심 과제.

**추가 확인(같은 날, 등록부 매칭률 실측)**: 한국 EEZ에서 실제 조업한 국내 어선
50척 표본 전부(0/50) GFW `registryInfo` 매칭이 없음 — `registryInfo`는 국제기구
등록(원양) 선박에만 붙는 것으로 보이며, 우리가 실제로 다룰 근해 모집단에는
구조적으로 적용 불가능. 또한 MOF API는 입력 파라미터가 `vsslNm`/`clsgn`뿐이라
MMSI(ssvid) 자체로 조회하는 경로도 없음 — 5번 단계에서 "이름 매칭 외 대안이
사실상 없다"는 전제를 놓고 다시 설계해야 함.

## 9. 어선원부 소스 이해 — 사용자 제공 파일로 확인 (사용자 제안, 2026-08-17)

사용자가 제안한 소스. "어선원부"는 어선법상 어선 등록 원장으로, TAC의 "어선번호"
체계와 직결될 가능성이 있어 확인. data.go.kr에 동명 유사 데이터셋이 2개
있었는데(`15115872`, `15147514`), 이 중 컬럼이 더 풍부한 `15115872`
(`해양수산부__어선원부`)를 사용자가 다운받아 제공.

### 발견 — 큰 잠재력

| 컬럼 | 의미 | 우리 스키마에서의 가치 |
|---|---|---|
| 어선번호 | 14자리 — **TAC 어선번호와 형식 일치 확인**(예: `00110046264405`) | TAC와의 조인키 후보 |
| 호출부호명 | 콜사인 | **GFW로 연결되는 다리 후보** |
| 엔진마력 | 개별 선박 마력 — 전체 1,379행 100% 채워짐(0~5700 범위) | GFW·MOF 둘 다 없던 **개별 마력의 실질적 원천** |
| 허가일련번호 | 허가 식별자 | TAC "어업 허가 번호"와의 연결 후보(형식 대조 필요) |

### ⚠ 심각한 제약 — 이 파일 자체는 실사용 어려움

| 문제 | 실측 |
|---|---|
| `현행여부` | **1,379행 전부 'N'** — 현재 유효 기록이 아닌 것으로 추정(공식 코드표 없이 필드명만으로 추정한 것이라 확정은 아님) |
| `등록처리일자` 범위 | **전부 2006-01-02~2006-12-29** — "2023-08-21 기준 스냅샷"이라는 페이지 설명과 실제 내용(2006년 처리 배치)이 어긋남 |
| 규모 | 1,379행뿐 — 전국 어선 수만 척에 비해 지나치게 적음. 페이지 확인 결과 "수시(1회성) 단일 파일"이며 연도별 추가 파일 없음 — 정부측 데이터 자체의 한계로 보임 |
| 호출부호 보유율 | 277/1,379(20.1%)만 콜사인 있음 — 나머지는 GFW로 연결할 다리 자체가 없음(소형 연안어선 다수가 국제콜사인 체계 밖이라는 도메인 예상과 일치) |
| Open API | **신청 불가 확인**(사용자 확인, 2026-08-17) — 파일 데이터가 유일한 접근 경로 |

**평가**: 이 소스는 "전체 모집단을 커버하는 원천"으로는 못 쓰지만, **일부 선박에 한해 개별 마력·콜사인을 보강하는 부분 소스**로는 가치 있음 — 매칭되는 선박만 마력값을 채우고, 매칭 안 되는 다수는 여전히 업종평균(어업별어선/TAC 업종집계)에 의존해야 함. 6번(모집단 범위)·5번(조인키) 단계에서 "보조 enrichment 소스"로 스키마에 반영 예정.

## 10. 해양기상 소스 이해 — 사용자 제공 매뉴얼 + 실제 호출로 확인

`data.go.kr`의 openapi.do 페이지는 이번에도 상세 스펙을 안 보여줬으나, 사용자가
국립해양측위정보원(marineweather.nmpnt.go.kr)의 공식 OPEN API 매뉴얼 원문을
그대로 제공 — 1차 자료로 확정.

| 확인 항목 | 결과 |
|---|---|
| 엔드포인트 | `http://marineweather.nmpnt.go.kr:8001/openWeatherNow.do`(최신) / `openWeatherDate.do`(날짜별) — **http(https 아님) + 8001 비표준 포트**, 방화벽 이슈 가능성 유의 |
| 파라미터 | `serviceKey/resultType(json,xml)/mmaf(기관코드=지방청)/mmsi(관측지점코드, 콤마로 복수)/dataType(1 또는 2)/date(날짜별 조회 시)` |
| ⚠ `mmsi` 파라미터 명칭 주의 | 이건 **선박 MMSI가 아니라 해양관측지점(등대·등부표) 코드**다 — 이름이 같아서 우리 스키마의 선박 MMSI(ssvid)와 혼동 주의 |
| `dataType` 차이 | 1(기본값)은 결측/미관측 항목을 응답에서 아예 제외 — **원칙1(원본 그대로 저장)과 충돌 소지**. 2는 "미제공"(장비 없음)과 "데이터없음"(장비는 있으나 이번 주기 결측)을 구분해 표시 — **수집 시 dataType=2를 기본으로 쓰기로 결정** |
| 관측지점 목록 | 매뉴얼에 지방청 13개(부산청~진도소) 산하 약 76개 지점의 코드·명칭·관측가능항목이 사전에 명시돼 있음 — 지점별로 관측 가능한 항목이 다 다름(시정만 재는 곳도 있고, 풍향·풍속·수온·염분·기온·습도·기압·유향·유속까지 완비한 곳도 있음) |

## 12. 조인 키(식별자) 설계 — 결정 사항

**허브 선정**: GFW의 vesselId를 허브로 삼는다 — A/B축 계산의 실제 재료(조업이벤트)를
가진 유일한 소스가 GFW라서, MOF/TAC/어선원부는 GFW가 찾은 배에 속성을 덧붙이는
역할이지 그 자체로 모집단을 만들 수 없음.

**매칭 전략 — 강한 신호부터 시도, 실패 시 약한 신호로 단계적 하강**:

| 단계 | 대상 | 방법 | 근거 |
|---|---|---|---|
| 1 | TAC ↔ 어선원부 | 어선번호(14자리) 정확일치 | 두 소스 다 14자리 동일 형식 확인됨(8·9번 참고) — 실제 겹치는지는 본수집 후 실측 검증 필요 |
| 2 | 어선원부 ↔ GFW | 호출부호(콜사인) 매칭 + 이름 교차확인 | 어선원부 콜사인 보유율 20%뿐이라 그 안에서만 적용. GFW `selfReportedInfo` 콜사인은 신뢰도 낮음(POLARIS PRINCE 사례)이 확인됐으므로 콜사인 일치만으로 끝내지 않고 이름도 같이 대조 |
| 3 | 나머지 전체 | 이름 + 톤수 + 활동해역(항구 인근) **다중신호 fuzzy 매칭** | 이름 하나만으론 정밀도 7.5~13.2%(이전 실측)로 개선 안 됐음(도메인지식 1번) — 독립적 신호를 겹치면 동명이인 충돌을 줄일 수 있다는 게 이번 설계의 핵심 차이점(단일 임계값 튜닝이 아님) |
| 4 | 그래도 미매칭 | 매칭 실패로 인정, 억지로 안 붙임 | `score/`·`ui/adapter.py`에 이미 "matchingFailed" 상태 처리 로직 존재 — 새로 만들 필요 없음 |

이 전략의 실제 정밀도(특히 3단계)는 본수집(7번) 이후 실데이터로 검증해야 확정.

## 13. 모집단 범위 확정 — 결정 사항

기획서 원안은 "1차 범위 = 근해어선, 연안 소형어선은 확대 로드맵"(2번 섹션
참고)이었으나, 오늘 확정한 모집단 정의(`flag='KOR'` AND 한국 EEZ 내 조업)는
근해뿐 아니라 연안 어선도 함께 잡힐 가능성이 높음.

**결정**: 근해/연안을 걸러내거나 미리 하나로 정하지 않고, **둘 다 넓게
수집한 뒤 "근해/연안" 태그만 붙여서 score팀이 나중에 선택하게 한다** —
원칙1(판단을 수집단계에 넣지 않음)과 같은 논리.

**태그 소스 2종(둘 다 부착)**:

| 태그 소스 | 방식 | 성격 |
|---|---|---|
| 어업허가 업종명 | "근해OO어업" vs "연안OO어업"처럼 업종명 자체에 근해/연안이 명시돼 있음(어업별어선 MR 데이터에서 확인) — TAC 등 업종 정보 있는 선박에 적용 | 제도(허가) 기준 |
| GFW `regions.eez` vs `regions.eez12Nm` | 이벤트 위치가 12해리 이내(eez12Nm)인지 전체 EEZ(eez)까지인지로 구분 — GFW 이벤트만 있으면 어업허가 정보 없어도 적용 가능 | 행동(실제 조업위치) 기준 |

### 추가 검토 (2026-08-17, "검토는 항상 해야한다")

| 항목 | 결정 |
|---|---|
| 모집단 조건의 이벤트 타입 | **FISHING 타입 한정으로 확정** — A축·B축 계산이 전부 `fishing.*` 하위필드에서 나오므로, FISHING 이벤트가 0건인 배는 애초에 점수 계산이 불가능함. "EEZ 내 FISHING 이벤트 1건 이상"이 모집단 조건 |
| 양식업 배제 여부 | **지금 거르지 않음** — 양식업 배는 고정 가두리를 매일 오가서 A축의 "재방문" 로직이 오인할 수 있다는 개념적 우려가 있으나, GFW가 실제로 양식업 배를 FISHING으로 잡아내는지 확인 안 됨. 근해/연안과 같은 논리로 **업종 태그(양식업 여부)만 붙여서 가공 단계로 미룸**(원칙1) |
| 모집단의 스냅샷 성격 | "그 시점 EEZ 조업이력 있는 배"로 정의하므로 재수집 때마다 구성원이 바뀔 수 있음 — 기존 스냅샷 원칙(3번)의 연장으로, 모집단 목록 자체도 스냅샷 대상임을 명시 |

## 16. 가공 파이프라인 — GFW 이벤트 정규화 (2026-08-17)

`data_new/process/normalize_gfw_events.py` — raw의 중첩 구조를 score/ 계약
(flat) 형태로 변환. raw/는 읽기만 하고, 산출물은 `processed/`에 새로 씀
(스냅샷 원칙 미적용 — 원본에서 결정론적으로 재생성 가능하므로 재실행 시
덮어써도 무방).

### 실제 발견: `fishing.averageDurationHours`가 사실상 항상 비어있음

수집한 19,613건 전수 확인 결과 `durationHours` 후보 필드
(`fishing.averageDurationHours`)가 **100% null**이었음 — 이대로 두면
B축(`axis_b_baseline.py`의 `REQUIRED_PHYSICS_FIELDS`)이 모든 행에서
스킵되어 전혀 계산이 안 됨.

**해결**: 모든 이벤트에 100% 존재하는 `start`/`end`(전수 확인, null 0건)로
`durationHours`를 직접 계산(`(end - start)`)하도록 정규화 로직을 바꿈 —
GFW 자체 필드를 신뢰하지 않고 우리가 가진 더 신뢰도 높은 원재료로 대체.
재실행 결과 null 0건, 중간값 2.9시간, 최대 144시간(6일) — 값 자체도
합리적 범위(예전에 봤던 14년짜리 이상치는 이번엔 안 나옴, FISHING 타입만
수집해서 LOITERING/PORT_VISIT의 장기 이상치 문제가 애초에 안 섞임).

### 매칭된 21건 교차검증 — 이름 불일치 다수 발견, 원인 확정 못함

일부(예: "제108제일호", "제2003금성호", "제308평산호")는 **이름·톤수
완전 일치** — 확실히 같은 배. 나머지 다수는 **어선번호는 같은데 이름이
전혀 다르고 톤수도 근소하게 다름**(예: 135 vs 139, 20 vs 19).

두 가설을 검토함:
- 가설 A(단순 개명): 20년 새 배 이름만 바뀜 — 근데 톤수가 완전히 안
  같은 사례가 많아 이 가설만으론 설명 안 됨
- 가설 B(대체건조): 같은 어업허가 슬롯(어선번호)을 유지한 채 배를
  통째로 새로 지음 — 이름 다르고 톤수 근소히 다른 패턴과 더 잘 맞음

어선원부의 **"연계어선번호"** 필드(13번에서 "의미 확인 필요"로 남겨뒀던
것)를 raw에서 직접 대조한 결과, **21건 중 3건은 이 필드가 명확히 채워져
있어 대체건조(가설B)가 실제로 일어나는 메커니즘임을 확인**. 나머지
18건은 이 필드가 비어있어 가설A/B 중 뭔지 이 데이터만으론 구분 불가
(최초등록일자가 대체로 1994~2004년으로 오래된 기록이라는 공통점만 있음).

**결론(잠정)**: 어선번호 조인키 자체는 유효해 보이나(3건에서 명시적
연계 확인), **어선원부의 마력·톤수 값을 "지금 이 배의 정확한 값"으로
확신하고 쓰면 안 됨** — 특히 최초등록일자가 오래된 경우 그 사이 대체건조
가능성을 배제 못함. 가공 단계에서 "불확실한 보조값"으로만 취급하고,
이름 일치 여부(가설A/B 구분 신호)를 신뢰도 등급에 반영하는 방향을 검토할
것(예: 이름도 일치하면 고신뢰, 어선번호만 일치하면 저신뢰).

## 19. 매칭 2단계 실행 — GFW ↔ 어선원부 콜사인 (2026-08-17), prefix 가설 폐기

`process/match_gfw_vessel_registry.py`. GFW `selfReportedCallsign`이 "306"
처럼 짧은 숫자인 경우가 많고 어선원부 콜사인은 "306평산호"처럼
숫자+이름 형태라, "GFW 콜사인이 어선원부 콜사인의 접두어인가"를 후보
신호로 시도.

**실측 결과: 폐기.** GFW 콜사인 "306" 하나가 어선원부의 **서로 다른 배
6척**(306평산호/306금영호/306봉화호/306정호/306민정호/306동성호 등)과

3자리 숫자 코드 자체가 개별 선박 고유값이 아니라 흔한 패턴(선적항·지역
코드류로 추정, 확인 안 됨)으로 보이며, prefix 매칭을 쓰면 TAC 이름매칭

**결정**: prefix 신호는 코드에서 제거, 콜사인은 **정확일치만** 신호로
인정. 표본이 작아(GFW 10척) 실제 정확일치 발생률은 아직 못 봄 — 본수집
후 재확인 필요.

## 20. 매칭 3단계 실행 — 이름 fuzzy 매칭 (2026-08-17)

`process/match_fuzzy_name.py`. GFW 로마자명과 TAC/어선원부 한글명을
직접 비교할 수 없어(문자 체계가 다름), `korean-romanizer` 라이브러리로
한글명을 로마자로 변환한 뒤 `difflib.SequenceMatcher`로 유사도 점수를
매김. **표준 로마자 변환 규칙과 정확히 같을 거라 가정하지 않고**(사용자
지적 — 자기신고자가 발음나는 대로 대충 썼을 수 있음) 정확일치가 아니라
점수 기반 순위만 산출, 자동 accept/reject는 안 함(옛 TAC 매칭이 정밀도
7.5~13.2% 한계에 부딪혔던 것 반복 방지).

**한계 확인**: GFW 쪽 톤수(`registryTonnageGt`)는 `registryInfo` 있는
소수에만 있어(우리 모집단 대부분 없음), 톤수 교차확인은 "있으면 보너스"
수준 — 이름이 사실상 유일한 상시 신호.

### 실측 결과 — 방법이 실제로 작동함을 확인

GFW 10척 표본에서 강한 매칭 다수 확인:

신호(항구 위치 vs 이벤트 좌표)는 아직 미구현.

## 21. 매칭 4단계 — 최종 조립 (2026-08-17)

`process/assemble_matches.py` — 2단계(콜사인 정확일치, 고신뢰) >
3단계(이름 fuzzy, 잠정 임계값 0.8 이상이면 중신뢰) > 매칭실패 순으로
GFW 선박별 최종 판정을 만든다. 매칭 실패해도 최고 후보와 점수를 같이
남겨 나중에 사람이 재검토할 수 있게 함(억지로 버리지 않음).

⚠ `FUZZY_NAME_THRESHOLD=0.8`은 표본 10척에서 강한 매칭(0.8~1.0)과 약한
매칭(0.55~0.72) 사이의 빈 구간을 보고 임시로 잡은 값 — 본수집 후 훨씬
큰 표본으로 재조정 필요.

**실행 결과(GFW 10척 표본)**: tier2 콜사인 0척(표본 작아서 예상대로),
tier3 fuzzy 7척(70%), 미매칭 3척(30%). 이 비율 자체는 표본이 작아 신뢰
못하지만, **파이프라인이 GFW 원본 → 정규화 → 매칭 → TAC 데이터 연결까지
끝에서 끝까지 작동하는 것을 확인**(예: `DEOG YANG HO` -> 어선원부
`95041176213504`, 유사도 1.0 완전일치).

**남은 것**: 해역 신호 추가, 임계값 본수집 후 재조정, MOF 데이터를
후보 풀에 포함시키기, 매칭 안 된 나머지 소스(TAC↔GFW 직접, 어선원부↔TAC
간 다른 조합)도 고려할지 검토.

## 22. 근해/연안·양식업 태그 구현 (2026-08-17)

6번(모집단 범위 확정)의 "필터 아니라 태그로 보류" 결정을 실제 구현.

**업종명→대분류 매핑표 재확인**: TAC 업종명에 항상 "근해"/"연안" 글자가
있는 게 아님을 재확인(예: "동해구기선저인망어업"엔 없지만 근해 카테고리) —
어업별어선(MR) 원본의 통계코드 체계를 실측으로 전부 확인(2019년, 가장
완전한 연도, 54개 코드)해서 `process/gear_type_categories.py`에 공식
계층구조(1000=원양/2000=근해/3000=연안/4000=양식/5000=내수면/6000=기타)
그대로 옮김 — 이름의 접두어가 아니라 이 코드 체계로 판단해야 함.

`process/tag_population.py` — 태그 2종:
- `locationTag`: GFW 이벤트의 12해리 이내(`eez12Nm`) 비율 — 어업허가
  정보 없어도 항상 계산 가능(행동 기준)
- `licenseTag`: TAC 매칭됐으면 업종명을 위 매핑표로 조회(제도 기준)

**실행 결과(2,562척, 이벤트 수집 테스트 배치 전체)**: `locationTag` 근해
1,783척(69.6%)/연안 779척(30.4%) — 합리적 분포. `licenseTag`는 전부
"미확인"(2,562/2,562) — 매칭 파이프라인을 10척 표본에만 돌렸으니 예상대로,
본수집 후 매칭 규모가 커지면 이 비율도 채워질 것.

## 23. 해양기상 부착 (2026-08-17)

**시간 정합성 문제 발견 및 해결**: `collect/marine_weather.py`를
`--date` 없이 돌리면 "최신"(수집 시점) 값만 나와서, 몇 주 전 이벤트에
그대로 붙이면 시간이 전혀 안 맞는 값을 붙이는 꼴이 됨 — 이벤트가 걸친
날짜(11개, 6/28~7/9)로 `--date`를 따로 수집해야 함을 확인.

**날짜별 조회 응답 구조가 최신조회와 다름을 실측 확인**: 지점당 값 1개가
아니라 **그 날 하루 전체의 10분 단위 시계열**이 옴(12지점×144건=1,728건
실측 확인) — 그래서 이벤트 시각에 가장 가까운 시간대를 골라야 함.

`process/attach_weather.py` — 이벤트 위치에서 최근접 관측소(Haversine
거리) 선정 → 그 관측소 시계열 중 이벤트 시각과 가장 가까운 레코드 선택.

**실행 결과(2026-07-05, 이벤트 2,295건 전부 부착)**:
- 시간 정합성: 매우 좋음(중간값 2.5분 차이, 최대 6.4분)
- **공간 정합성: 문제**(중간값 24.7km, 최대 251.4km 떨어진 관측소 값을
  붙인 경우 있음) — 관측소가 전국 76개뿐이라 구멍 있는 건 당연하지만,
  250km 거리는 그 지점 날씨를 대표한다고 보기 어려움

**결정**: 거리로 거르지 않는다(원칙1 연장) — `weatherStationDistanceKm`을
모든 레코드에 항상 같이 남겨서, 얼마나 멀리서 가져온 값인지 후속 단계가
알고 판단하게 함. 임계값(몇 km 이상이면 결측 취급할지)은 지금 안 정하고
미룸.

## 39. 톤수 이상치(max 140,979 GT) 원인 규명 — MOF 후보풀 오염 (2026-08-17)

37번에서 찾은 톤수 이상치의 실제 선박을 역추적: 상위 15개 전부

우연히 대형 상선(외항 화물선·유조선 등)의 실제 선명과 일치해버리면

전혀 다른 배라는 뜻. 이름 매칭만으로는 원천적으로 못 걸러내는 오류
유형.

확인 — `vsslKnd`(선박종류) 필드가 각각 `41[풀컨테이너선]`,
`21[산물선(벌크선)]`, `21[산물선(벌크선)]`이었고 `vsslNlty`(국적)도

어선이 아니라는 게 원본 필드로 명확히 확인됨.

**결론**: 38번(흔한 한글 어선명 충돌)과는 다른 별개의 원인. **MOF
후보풀에서 `vsslKnd`로 어선이 아닌 선박(상선·여객선 등)을 애초에
걸러내는 게 근본 해결책** — `normalize_mof.py`가 이미 `vsslKnd` 필드를
받아두고 있는데 `match_fuzzy_name.py`가 이를 전혀 안 쓰고 있었던 게
원인(활용 여지 새로 확인). 코드 수정은 안 함 — 이것도 회의 안건.

것 중 번호가 어긋나는 78건은 재검토 후보. 회의 안건(38번)에 이 정량
결과 추가.

## 45. MOF 활용도 낮은 원인 규명 — "이름표기 불일치"가 아니라 구조적 문제

지금까지 "MOF 활용도 낮음(쿼리 4,662건 중 후보 1,770건)"을 "이름표기
불일치 추정"으로만 적어뒀는데, 실제로 파봄.

**1단계 — 응답 자체가 비는 비율**: 쿼리 4,662건 중 **89.9%(4,189건)가
아예 `totalCount=0`**(원본 XML로 직접 확인, 파싱 버그 아님). 후보가
나온 건 473건(10.1%)뿐.

**2단계 — 나온 후보들의 정체**: 성공한 473건의 후보를 까보니 전부
`vsslEngNm`(영문명) 필드가 쿼리어와 정확히 일치/포함하는 경우였고,
`vsslKnd`를 보면 거의 다 **상선류**(석유제품운반선·LNG운반선·
케미칼운반선·벌크선·일반화물선 등)였다 — 39번에서 찾은 상선 오염과
같은 뿌리.

**근본 원인**: GFW 자기신고명은 항상 로마자(영문)인데, MOF 검색이
사실상 `vsslEngNm`(영문명) 매칭이고, **국내 소형 연근해 어선은
`vsslEngNm`이 거의 안 채워져 있다**(영문명은 주로 국제항해를 하는
상선급 선박에만 등록됨) — 그래서 로마자 이름으로 검색하면 구조적으로
소형 어선을 거의 못 찾고, 어쩌다 걸리는 것도 영문명이 있는 상선일
확률이 높다. "이름표기가 미묘하게 달라서"가 아니라 **애초에 검색
대상 필드에 우리가 찾는 모집단(소형 어선)의 데이터가 거의 없는 것**.

**수치로 확인**: MOF 후보 전체 1,770건 중 어선(vsslKnd 91/92) 코드는
196건(11.1%)뿐 — 전체 쿼리 4,662건 기준으로는 **실질 기여율 약 4.2%**.
TAC(2,242척 기여)·어선원부(551척 기여)에 비해 MOF의 실효성은 원래
기대보다 훨씬 낮다.

**결론**: MOF는 이번 모집단(근해/연안 소형 어선)에는 구조적으로 안
맞는 소스에 가깝다 — 재설계(예: 로마자 대신 다른 검색 전략)는 지금
당장 하지 않고, 우선순위를 낮추는 정도로 팀에 공유. 코드 수정 없음.

## 46. 어항정보(113개) 실효성 정량 확인 — 커버리지 훨씬 낮음

"어항정보는 113개뿐이라 커버리지 낮다"는 이전부터 알던 한계였는데,
실제 매칭 파이프라인에서 얼마나 쓰이고 있는지 처음으로 정량 확인.

- **TAC에 항구정보 있는 선박 1,990척 중, 그 항구명이 우리 113개
  리스트에 실제로 있는 경우는 102척(5.1%)뿐**. 344개의 고유 항구명이
  리스트에 없음.
- 매칭 3단계(fuzzy) 전체 4,662척 기준으로 봐도, 위경도 거리 기반
  해역보너스(`locationBonus`)가 실제로 계산된 건 460척(9.9%)뿐 —
  거의 안 쓰이고 있는 신호.
- 미커버 항구명 중 상당수가 "통영시"/"진해시"/"홍성군"처럼 **특정
  항구가 아니라 행정구역명**이라, 113개를 단순히 더 늘린다고 바로
  해결되는 게 아니라 **TAC의 `portNamesTac` 값 자체가 항구명과
  행정구역명이 섞여 있는 형식 문제**도 같이 있음.

**결론**: 해역보너스는 지금 사실상 유명무실한 신호(9.9%만 작동) —
"113개뿐이라 낮다"보다 훨씬 심각한 수준. 항구 리스트 확장 전에
TAC `portNamesTac`을 항구명/행정구역명으로 먼저 정리(가공 단계 개선)
하는 게 선행돼야 확장 효과가 제대로 날 것으로 보임. 코드 수정 없음,
회의/우선순위 논의용 발견.

## 47. score/ 필드명 계약 검증 — A축은 문제없음, B축은 연결 스크립트 없음

`score/axis_a_pressure.py`, `axis_b_baseline.py`, `axis_b_physics.py`,
`peer_grouping.py` 코드를 직접 읽어 우리 `processed/` 산출물과 실제로
맞는지 대조.

**A축(`compute_axis_a_pressure`) — 문제없음**: 필요 필드
`eventId`/`vesselId`/`start`/`latitude`/`longitude` 전부 우리
`gfw_events_normalized.jsonl`과 이름·구조가 정확히 일치. **그대로
넣고 바로 돌릴 수 있음.**

**B축(`compute_axis_b_efficiency` + `fit_baseline_model`) — 이어주는
스크립트가 없음**: 이 함수들은 이벤트 1건당 아래 필드가 **한 딕셔너리
안에 다 모여있는** `rows`를 요구한다:
- `tonnageGt`, `averageSpeedKnots`, `durationHours`(물리식 필수 3종)
- `seaSurfaceTempC`, `windSpeedMs`, `currentSpeedMs`, `totalDistanceKm`(LightGBM 수치 피처)
- `gearType`, `seaArea`, `season`(LightGBM 범주형 피처)

그런데 우리 산출물은 이게 전부 **따로따로 흩어져 있다**:
- `tonnageGt`는 아예 없음 — `final_vessel_matches.jsonl`엔
  `tac.tonnageGtTac`/`mof.tonnageGtMof`로 중첩돼 있음
- 해양기상은 필드명 자체가 다름 —
  `weather_WATER_TEMPER`/`weather_WIND_SPEED`/`weather_SURFACE_CURR_SPEED`
  (해양기상 API 원본 필드명 그대로) vs score/가 기대하는
  `seaSurfaceTempC`/`windSpeedMs`/`currentSpeedMs`(단위까지 다를 수
  있음, 미확인)
- `gearType`/`seaArea`/`season`은 지금 어느 processed/ 파일에도 이
  이름 그대로는 없음(`gear_type_categories.py`의 근해/연안 분류,
  `peer_grouping.py`의 `region_key()`/`season_key()`는 자체적으로
  lat/lon/start에서 즉석 계산하므로 이건 B축 LightGBM 피처와는
  별개 — 이름이 겹쳐서 헷갈리기 쉬움)

**결론**: `events_with_weather.jsonl` + `final_vessel_matches.jsonl`을
합쳐서 B축이 기대하는 flat `row` 형태로 만드는 **연결 스크립트가
`process/`에 아직 없다** — "데이터가 없어서" 못 도는 게 아니라
"이어주는 코드가 없어서" 못 도는 상태. 이건 데이터팀 산출물과 score/
팀 계약 사이의 간극이라 어느 쪽이 만들지(데이터팀 `process/` 확장 vs
score/ 팀 adapter) 논의 필요 — 지금은 발견만 하고 코드 작성은 안 함.

## 48. 구(`bluescore/data/`) 파이프라인과 비교 + 매칭 정밀도 재검증 — 심각한 하향 수정

이번 재구축은 "data 폴더가 비어있다고 생각하고" 처음부터 다시 만든
것이었는데, 다 끝난 시점에 구 파이프라인 문서(`BlueScore_데이터파이프라인_현황.md`,
`BlueScore_TAC매칭_임계값_실측분석.md`, `BlueScore_발표대비_데이터실측치.md`,
전부 김태윤 작성, 2026-08-15)와 대조해봤다.

**구조적으로 새 파이프라인이 나은 점**: 모집단 정의(구는 GFW
`shiptypes=FISHING` 자기신고 31,605척, 새 것은 EEZ+FISHING 이벤트
행동증거 기반 5,323척), 실규모 수집 체계, MOF 비어선 오염 근본수정
(39·41번), score/ 필드명 코드 대조(47번) 등.

**구 파이프라인에만 있던 것 — 정밀도 실측 검증 방법론**: 구
분석(`TAC매칭_임계값_실측분석.md`)은 MOF의 "비어선 의심" 신호를
정답 대용으로 써서 TAC 이름매칭 정밀도를 임계값 0.70~0.98 전 구간
실측했고, **7.5~13.2%로 낮고 임계값을 올릴수록 오히려 떨어진다**는
결론(동명이인 문제)을 냈다. 우리(40번)는 이걸 안 하고 육안 표본
판단(체감 80~85%)으로만 평가했었다 — 훨씬 느슨한 검증.

**그래서 같은 방법론을 우리 데이터에 재적용**(`analysis/
explore_match_precision_groundtruth.py`, 읽기전용): tier3(TAC/어선원부
출처) 매칭 2,845척 중, 그 매칭과 무관하게 독립 수집해둔 MOF 원본
검색결과가 있는 233척만 검증 가능(대상 자체가 적음, 구 분석의 572건과
비슷한 제약). GFW 자기신고명과 아주 비슷한 MOF 후보가 있는데 그 후보의
`vsslKnd`가 어선이 아니면 "충돌"로 카운트.

| 임계값 | 검증가능 | 충돌없음 | 충돌 | 정밀도 하한 |
|---|---:|---:|---:|---:|
| 0.80 | 233 | 52 | 181 | **22.3%** |
| 0.85 | 173 | 33 | 140 | 19.1% |
| 0.90 | 109 | 18 | 91 | 16.5% |
| 0.95 | 69 | 8 | 61 | 11.6% |
| 0.98 | 68 | 8 | 60 | 11.8% |

**구 분석과 사실상 같은 패턴이 재현됨**: 임계값을 올릴수록 정밀도가
오히려 떨어진다(22.3%→11.6%), 절대 수준도 구 분석(7.5~13.2%)과 같은
자릿수. 40번의 "체감 80~85%"는 **육안 판단이 정답신호 기반 검증보다
훨씬 낙관적이었다는 뜻** — 이 정밀도하한 수치가 더 신뢰할 만하다.

**중요한 해석상 주의**: 이건 "정밀도 하한"이지 실제 정밀도가 아니다
(충돌 신호가 없다고 다 맞다는 보장은 없음 — MOF에 검색이 아예 안
걸리면 충돌 여부 자체를 못 잼). 그리고 검증 가능한 표본이 233척뿐이라
(tier3 전체 2,845척의 8.2%) 전체로 일반화하기엔 표본이 작다. 그래도
구 분석과 독립적으로 같은 결론이 재현된 건 우연이 아닐 가능성이 높다.

**결론 — 팀 공유 시 반드시 같이 전달**: "매칭률 54.1%"라는 숫자를
그대로 "이만큼 정확히 식별했다"로 쓰면 안 된다. 실제 정밀도는 구
분석·이번 재검증 둘 다 10~20%대를 가리킨다. B축에 tier3 매칭 결과를
쓸 때는 이 낮은 정밀도를 감안한 가중치나, 더 엄격한 재검증(구 분석이
제안한 "TAC 어선번호-국내 등록번호 공식 대조표 확보" 같은 근본 해결)
없이는 위험할 수 있음 — 회의 안건에 최우선으로 추가.

**추가 시도(검증 불가로 결론)**: 44번의 "숫자접두어 일치 신호"가 이
정답신호 검증에서도 실제로 정밀도를 높이는지 교차확인 시도. 결과 —
번호패턴으로 판단 가능한 233척(44번)과 MOF 교차검증 가능한 233척
(48번)이 **겹치는 게 1건뿐**(거의 딴 표본) — 통계적으로 검증 불가능.
44번 가설은 이 방법으로는 확인도 반박도 못 함, 별도의 검증 방법이
필요(예: 사람이 직접 표본 라벨링).

## 49. 사람 라벨링 결과 — 48번을 뒤집는 반전, 정밀도는 훨씬 높았음

라벨링 아티팩트(층화 랜덤추출 80쌍: matched 0.8~1.0 15개씩 + unmatched
근접점수 20개)를 팀원이 직접 라벨링해 `match_precision_labels.json`으로
전달받음. `analysis/analyze_human_labels.py`로 분석.

**결과 — 48번과 정반대 패턴**:

| 구간 | n | 정밀도(애매 제외) |
|---|---:|---:|
| matched 0.80~0.85 | 15 | 57.1% |
| matched 0.85~0.90 | 15 | 75.0% |
| matched 0.90~0.95 | 15 | 75.0% |
| matched 0.95~1.00+ | 15 | **92.9%** |
| **matched 전체** | 60 | **75.0%** |
| unmatched 근접점수(0.70~0.80) | 20 | 40.0%(구제 시) |

**임계값을 올릴수록 정밀도가 오히려 올라간다** — 48번(MOF 교차검증)·
구 파이프라인 분석에서 본 것과 정반대 패턴. 40번의 육안 판단(체감

번호 일치는 사실상 확정적 신호, 번호 불일치는 표본은 작지만(n=3+2=5)
**5건 전부 틀림** — 44번에서 제안한 "번호 일치 134척 타겟 구제 +
기존 매칭 중 번호불일치 78척 재검토"가 이 결과로 뒷받침됨.

**왜 48번·구 파이프라인과 이렇게 다른가 — 표본 편향으로 추정**: 48번의
"검증 가능" 대상은 **GFW 자기신고명이 MOF 검색에도 걸리는 선박만**
이었다(233/2,845, 8.2%). 45번에서 이미 확인했듯 MOF 검색은 영문명
매칭이고, 소형 어선은 영문명이 거의 없어 MOF에 걸리는 이름은 대개
"SPEED"/"POINT" 같은 **짧고 흔한 영단어**다 — 이런 이름은 애초에
동명이인 충돌 위험이 큰 부분집합이라, 48번 표본은 "매칭 후보 전체"가
아니라 "가장 위험한 부분집합"만 본 것으로 보인다. 구 파이프라인의
7.5~13.2%도 TAC↔**MOF 경유** 매칭만 분석한 것이라 같은 편향을 공유할
가능성이 있다. 반면 이번 80쌍은 **점수구간별 층화 랜덤추출**이라 이
편향이 없고, 전체 매칭 후보를 대표하는 값에 훨씬 가깝다.

**결론(48번 경고를 수정)**: "매칭률 54.1%" 중 실제 정밀도는 48번이
시사했던 11~22%가 아니라 **약 75%(0.95+ 구간은 92.9%)로 보는 게
더 타당**하다. 다만 표본이 80개뿐이라 오차범위는 있고, 48번이 짚은
"MOF 경유 매칭은 특히 위험하다"는 결론 자체는 여전히 유효 — 그
부분집합(191척, tier3의 6.6%)만 낮은 정밀도로 따로 취급하는 게
합리적. 이제 실행 가능한 구체안: **번호일치 신호로 unmatched 134척
타겟 구제 + 기존 매칭 중 번호불일치 78척 재검토·제외**(44번) —
정밀도 개선과 구제 둘 다 되는 안.

## 50. 매칭을 로마자 유사도에서 한글 직접비교로 교체(채택) — 44번 이후 상황이 바뀜

44번(숫자신호로 78척 제외+134척 구제) 검토 도중, GFW 영문명 4,662척
전체를 사람이 직접 한글로 재변환한 데이터(`gfw_korean_name_candidates.csv`)
가 새로 생겼다 — 이러면 44번처럼 로마자 유사도를 패치하는 것보다,
애초에 로마자 변환 자체를 건너뛰고 한글 원문끼리 직접 비교하는 게
근본적으로 나을 수 있어 그 방향으로 전면 재검토했다.

**발견**: 로마자 유사도는 서로 다른 실제 이름인데 로마자로 바꾸면
끝부분이 겹쳐서 점수가 높게 나오는 구조적 오탐이 있었다(예:
EUNSEONGHO(은성호)가 금성호로, DEOG YANG HO(덕양호)가 동양호로
오매칭). 한글 직접비교(exact match만)로 바꾸면 이 문제가 원천적으로
없어진다. 검증 과정에서 여러 버그를 사람이 직접 웹 탐색기를 훑어보며
찾아냄(자동 검증만으론 놓쳤을 패턴들) — "제N호" 내부번호 소실,
지오코딩 실패를 "후보 아님"으로 오판, 숫자 하드필터의 자릿수 사각지대
등. 전체 검증 기록은 `data_new/matching_redesign_proposal/README.md`.

**최종 설계**: (1) 한글 exact match만 사용(fuzzy 폐기), (2) 숫자
하드필터를 자릿수 제한 없이 통일(양쪽 다 숫자 보이는데 다르면 배제),
(3) "제N호" 선단번호 정규화, (4) 카카오 지오코딩(로컬 API)으로 동률
후보를 거리(≤150km, 근해어업 조업범위 감안)로 판단 — 후보 전원의
위치를 모르면 확정하지 않음. gearType 보조필터와 헝가리안 전역할당도
시도했으나 실익이 작거나(gearType) 오탐률이 높아서(헝가리안 19%)
최종안에서는 뺐다.

**결과**: matched 2,881척(54.1%, 추정 오탐 ~720척) → verified
1,290척(24.2%, 추정 오탐 거의 0). 커버리지는 줄고 정밀도는 크게
오름 — 오탐 하나가 B축 점수를 그 배 단위로 완전히 틀어지게 만들 수
있어 커버리지보다 정밀도를 우선하기로 결정(CLAUDE.md 12번). MOF 경유
매칭(45·48·49번에서 특히 위험하다고 지적된 부분집합)은 이번 설계에서
아예 후보풀에서 뺐다 — 이름 검색 자체가 어선보다 상선 위주로 편향돼
있어 얻는 것보다 오염 위험이 컸다.

`data_new/process/match_fuzzy_name.py`·`assemble_matches.py`에 반영,
`final_vessel_matches.jsonl` 재생성 완료(2026-08-18). `korean-romanizer`
의존성 제거, 카카오맵 API(`KAKAO_API_KEY`) 의존성 추가.

## 51. verified 기준에서 "이름만으로 확정"(거리 미확인 28척) 제외 — 예외 없이 단일화(2026-08-18)

낫다고 판단, `distKm is not None and distKm <= 150`으로 단일화 —
후보 개수와 무관하게 거리를 모르면 무조건 held_multi로 보류한다.

**결과**: verified 1,290척 → **1,262척**(28척은 held_multi로 이동,
1,402→1,430척). `final_vessel_matches.jsonl` 재생성 완료.

## 52. 어선원부를 후보풀에서 완전히 제외 — GFW-TAC 매칭만 사용(2026-08-18)

51번까지도 `match_fuzzy_name.py`의 후보풀은 TAC와 어선원부를 같이 썼다.
어선원부는 전체 등록대장이 아니라 2006년 처리배치 일부(1,379행, 전부
현행여부='N')라 TAC보다 신뢰도가 떨어지고, 별도 경로였던 2단계
(GFW<->어선원부 콜사인 정확일치)도 기여분이 0.1%(3척)뿐이라 사실상
의미가 없었다. 정리 겸 사용자 결정으로 어선원부를 완전히 빼고
GFW-TAC 매칭만 쓰기로 확정했다.

**삭제한 것**: `process/match_tac_vessel_registry.py`(1단계),
`process/match_gfw_vessel_registry.py`(2단계), `process/
normalize_vessel_registry.py`, 그 산출물(`vessel_registry_normalized.
jsonl` 등 3개, 원래도 git 비추적). `assemble_matches.py`는 1·2단계
분기를 걷어내고 verified/unmatched 두 카테고리만 남기게 단순화(필드는
그대로 `matchTier`/`tac`/`mof` 유지, `mof`는 여전히 None — B축 소비
코드는 값 안 봐서 영향 없음, 50번에서 확인함).

같은 정리 과정에서 MOF 수집·정규화 스크립트(`collect/mof.py`·
`mof_korean_retry.py`·`hangul_reverse.py`·`process/normalize_mof.py`)도
삭제했다 — 매칭 후보풀에서는 이미 50번에서 빠졌고(오탐 위험,
MOF 경유 저정밀도), 라이브 파이프라인 어디서도 더 이상 안 읽었다
(`assemble_matches.py`가 `mof`를 항상 None으로 채움). 유일한
소비처였던 `analysis/explore_match_precision_groundtruth.py`(48번
분석, 49번에서 이미 결론이 뒤집힘)도 같이 삭제. 미사용 1회성
스크립트 `collect/static_files_check.py`, 미커밋 실험
`collect/mof_from_tac.py`도 정리.

**결과**: verified 1,262척(23.7%) → **1,234척(23.2%)**, held_multi
1,430→1,249척, unmatched 1,847→2,056척. `final_vessel_matches.jsonl`
재생성 완료. 파이프라인이 GFW 이벤트/선박 수집 → TAC 정규화 → 한글
직접비교 매칭으로 단순해짐(`data_new/README.md` 실행 순서 갱신).

## 53. TAC 쪽 유일성 강제 — verified의 63.8%가 같은 TAC 배 중복배정이었음(2026-08-18)

52번 결과를 발표 대비 방어 논리 점검 중 verified 25쌍을 무작위로 뽑아
사람이 직접 눈으로 확인했다(GFW 자기신고명 로마자 ↔ TAC 한글명이
말이 되는지). 대부분 정상이었지만 "1 DONG IL"과 "2023 DONG IL HO"라는
**서로 다른 GFW 선박 2척**이 TAC의 **같은 배** "동일호" 하나에 동시에
매칭돼 있는 걸 발견 — 확대 조사 결과 verified 1,234척 중 **787척
(63.8%)**이 같은 문제였다. distinct TAC 배는 714척뿐인데 267척
(37.4%)이 2개 이상의 GFW vesselId한테 동시에 "정답"으로 잡혀 있었음.
극단 사례: TAC "한성호" 1척이 GFW 쪽 서로 다른 vesselId **9개**한테
전부 매칭됨.

**원인**: 1~4단계(match_fuzzy_name.py)가 GFW 선박마다 독립적으로
판정하기 때문에 TAC 쪽 유일성을 전혀 체크하지 않았다. 숫자 없는 흔한
이름(한성호·동일호·대양호류)은 TAC엔 그 이름 배가 1척뿐이라도 GFW
쪽엔 이름이 비슷한 실제로 다른 배가 여러 척 있을 수 있는데, 그 여러
척이 전부 그 TAC 배 하나를 "유일한 이름일치 후보"로 잡고 거리
(≤150km)까지 우연히 통과하면 전부 verified가 됐다.

**수정**: `match_fuzzy_name.py`에 5단계 추가 — 4단계까지 마친 뒤 TAC
등록번호(`vesselNoTac`)별로 재집계해서, 같은 TAC 배를 여러 GFW
선박이 주장하면 조업위치가 가장 가까운 하나만 verified로 남기고
나머지는 held_multi로 되돌린다(동률 0.05km 이내면 전부 되돌림, 기존
`_try_resolve_by_nearest`와 동일 원칙).

**남은 한계**: "가장 가까움"은 확률적 근거지 증명이 아니다. 해결된
267개 충돌 중 승자-2위 마진이 10km 이내인 경우가 83건(31.1%), 1km
이내도 16건(6.0%) — 이벤트 중심점 평균·카카오 지오코딩 오차 범위
안일 수 있어 이 구간의 승부는 통계적으로 약함(median 마진 21.9km로
대부분은 여유 있음). 완전한 해결은 아니고 중복 배정이라는 명백한
오류를 없앤 것으로 이해해야 함.

**결과**: verified 1,234척(23.2%) → **713척(13.4%)**, held_multi
1,249→1,770척. TAC 배 중복배정 0건 확인(재검증 완료).
`final_vessel_matches.jsonl` 재생성 완료. 전체 검증 과정은
`data_new/matching_redesign_proposal/README.md`의 "TAC 유일성 강제"
섹션.

**참고(사후 산술 확인)**: 옛날 로마자 유사도 시스템(50번에서 폐기)은
TAC(1,993)+어선원부(1,379)=합쳐서 최대 3,372개 후보로 matched
2,881척을 냈다 — 전체 후보의 85%를 소진한 셈이다. 로마자 유사도는
지금 방식(정확일치+숫자+거리)보다 훨씬 느슨한데 후보 풀이 이렇게
좁았던 걸 보면, 이번에 발견한 "TAC 중복배정" 문제가 옛날 시스템에서는
더 심하게 있었을 가능성이 높다(코드가 이미 삭제돼 재검증은 불가 —
산술적 정황 증거로만 남김). 49번 사람 라벨링이 찾은 "로마자 끝부분
겹침" 오탐과는 별개의 추가 오탐 경로였을 수 있음.

## 54. GFW registryInfo 있는 선박(원양선 추정) 후보풀에서 제외(2026-08-18)
