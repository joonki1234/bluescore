# BlueScore 데이터 파이프라인 재구축 — 진행 기록

> `bluescore/data/`(구)는 참고하지 않고 처음부터 다시 설계한다. 수치·결론이
> 아니라 **무엇을 왜 그렇게 정했는지(결정 근거)**를 남기는 문서. 시행착오
> 서술은 빼고 최종 결정과 근거만 남긴다(2026-08-19 압축).

## 진행 상태

| 단계 | 상태 | 비고 |
|---|---|---|
| 1~9. 도메인 조사·스키마·수집원칙·소스 sanity call·조인키·모집단 확정 | 완료 | 아래 1~14번 |
| 10. 본수집(raw) | 완료 | GFW 이벤트 276,562건·선박 5,323척·해양기상 4/1~8/14·MOF 4,662건 |

## 1. 도메인 지식 — 재확인 필요 항목으로 시작한 가설들

TAC↔GFW 공통키 없음(어선번호 vs MMSI/콜사인/IMO), 국내↔GFW 어법분류
해상도 다름, GFW 이벤트는 AIS 궤적 추론(직접관측 아님), AIS 속도는
대지속도, "자원압력"은 CPUE 대체재 아니라 조업노력 집중도 — 전부 이후
단계에서 실측으로 확인/반영됨(아래 각 항목 참고).

## 2. 기획서(2026-08-11) 대조

TAC는 업종단위 보정계수가 원안이었으나 개별 선박 이름매칭으로 스코프
확장, 혼잡가중압력 기준값(연안AIS)은 미확보라 GFW 이벤트 밀도로 대체,
개별 선박 마력은 공개데이터에 없어 업종평균(어업별어선/TAC)이 유일한
출처, 모집단은 "근해 1차 한정" 원안 대신 EEZ+FISHING 이벤트 기준으로
연안까지 포함.

## 3. 데이터 정의(스키마) — 결정 사항

엔티티: Vessel/FishingEvent/WeatherObservation/CongestionBaseline
(`SCHEMA_DRAFT.md`). 필드명은 `score/`·`chain/`·`explain/`·`ui/`가 이미
요구하는 이름을 그대로 계약으로 확정(재작성 대상 아님). 법령/제도
정보(금어기 등)는 explain/ 담당이라 스코프 제외.

## 4. 수집 원칙(방법론) — 결정 사항

원본은 가공 없이 그대로 저장(판단 로직을 저장 시점에 넣으면 나중에
틀렸을 때 재현 불가), 재조회는 기본 스냅샷(덮어쓰지 않음), 일시적
에러(429/500/502/503)만 재시도(2s→4s→8s, 최대 3회), 항목 하나 실패해도
전체 수집은 계속, 진행상태 기록 후 이어받기(조건 다르면 새로 시작),
인증키는 `.env`+`.gitignore`(git 히스토리 영구잔존 우려), 소스별 폴더
분리, 요청 파라미터만 메타로 기록, 건수·구조·스냅샷보존·키비노출 4종
검증게이트, 조회기간은 실행 파라미터로(코드 하드코딩 금지), 스냅샷은
항상 최신 파일 자동탐색. 출처 신뢰도 우선순위: ①실제 API 호출
②공식 소스코드 ③1차 공식문서 ④공식 웹페이지 ⑤검색요약 — 기억·추정은
검증 전까지 근거로 안 씀.

## 5. GFW 소스 — sanity call + 공식 소스코드로 확정

Vessels Search는 `where`/`query`, `datasets`는 `public-global-vessel-identity:latest`만
유효. Events는 **POST**(공식 클라이언트 소스코드로 확인, 기억은 GET이라
틀렸었음), 이벤트 타입 6종(ENCOUNTER/FISHING/GAP/GAP_START/LOITERING/
PORT_VISIT). 원본은 중첩 구조(`vessel.id`, `position.lat/lon` 등),
score/ 계약 필드는 flat — 정규화 단계에서 변환 필요.

**결정적 발견**: `flag='KOR'` 단독 필터엔 원양 대형선단이 섞임(예:
서아프리카 해역에서 조업하는 KOR선적 실측 확인) — **국적이 아니라
실제 조업 위치(한국 EEZ 내)로 모집단을 정의**하기로 전환. 실측 검증:
`region: public-eez-areas #8327` + `flags:["KOR"]`로 실제 호출해
국내 어선 특유의 "OO호" 작명 패턴 확인. **모집단 확정: `flag='KOR'`
AND 한국 EEZ 내 FISHING 이벤트 1건 이상.**

기타: GFW 자체 마력 데이터는 API 응답에 없음, `registryInfo.geartypes`는
RFMO 등록선에만 주로 채워짐, PORT_VISIT/LOITERING엔 수년짜리 장기
이상치 존재(알고리즘 구조적 특성으로 추정).

## 6. MOF(선박제원정보) 소스 — sanity call 결과

엔드포인트 `SicsVsslManp3/Info3`(GET/XML), `vsslNm`은 부분일치 검색.
`vsslKnd`(선박종류)에 "어선" 카테고리 존재하나 이름검색만으론 대부분
비어선이 걸림.

**결정적 발견**: GFW `selfReportedInfo`(자기신고 콜사인/IMO)를 그대로
MOF에 조회하면 전혀 다른 배가 나옴(실측 확인, 예인선 사례) —
**`registryInfo`(공식 매칭)만 신뢰 가능**, `selfReportedInfo`는 신뢰
불가로 확정. 추가로 한국 EEZ 실조업 국내어선 50척 표본 전부(0/50)
`registryInfo` 매칭 없음 확인 — 근해/연안 모집단엔 이 필드가 구조적으로
거의 없음.

## 7. TAC(할당 승인 정보) — 사용자 제공 파일로 확인

data.go.kr Open API는 공공기관 전용이라 파일 다운로드로 전환. **CP949
인코딩**(UTF-8 아님), 컬럼 28개(어선번호 14자리·톤수·마력·어선명 한글
표기·양육항구 등), 식별자는 어선번호/어선명/어업허가번호뿐(콜사인·IMO·MMSI
없음). TAC 어선번호(14자리)와 MOF `vsslNo`(6자리)는 서로 다른 체계.

## 8. 어업별어선(MR) — 사용자 제공 파일로 확인

연도×업종 집계(개별 선박 아님, 1992~2020). **원양/근해/연안/양식/
내수면/기타 공식 분류 체계(통계코드 1000~6000) 발견** — GFW EEZ 기반
행동추정 분류와 성격이 달라 둘 다 확보해서 병행 사용하기로 결정.
업종명 컬럼에 불규칙 공백 있어 정규화 필요(기록만, 조치는 가공단계).

## 9. 어선원부 — 사용자 제공 파일로 확인 (사용자 제안)

어선번호(14자리, TAC와 형식 일치)·호출부호·엔진마력(1,379행 100%
채워짐) 등 잠재력은 있으나, **현행여부 전부 'N', 등록처리일자 전부
2006년, 총 1,379행뿐, 콜사인 보유율 20.1%**라는 심각한 제약 확인 —
전체 모집단 커버는 못 하고 일부 보강용 부분소스로만 취급하기로 결정.
(2026-08-18: 신뢰도 문제로 최종 매칭에서 완전히 제외, 50·52번 참고.)

## 10. 해양기상 — 사용자 제공 매뉴얼 + 실제 호출로 확인

엔드포인트는 http+8001 비표준 포트. `mmsi` 파라미터는 선박 MMSI가 아니라
관측지점 코드(혼동 주의). `dataType=2`로 "미제공"/"데이터없음"을
구분해서 수집하기로 결정(원칙1과 일치). 전국 76개 지점 전부 파고
센서 없음(구조적 한계, 확정). 관측소 좌표(LATITUDE/LONGITUDE) 포함돼
있어 최근접 매칭에 활용.

## 11. 추가 후보 소스 트리아지

연안AIS(별도 인증 필요, 보류)·개별선박 어업허가 현황(전국 데이터
없음, 보류)·해양보호구역(GFW `regions.mpa`로 대체 가능, 보류)·자원평가
(구조화 데이터 없음, 보류) — 4개 다 우선순위 낮음으로 결론.

## 12. 조인 키(식별자) 설계 — 결정 사항

**허브는 GFW vesselId** — A/B축 재료(조업이벤트)를 가진 유일한 소스.
매칭은 강한 신호부터 단계적 하강: ①TAC↔어선원부 어선번호 정확일치
②어선원부↔GFW 콜사인+이름 교차확인 ③나머지는 이름+톤수+해역
다중신호 fuzzy ④그래도 안 되면 매칭실패 인정(억지로 안 붙임,
`ui/adapter.py`의 기존 matchingFailed 처리 재사용).
(2026-08-18 재설계로 ①②는 폐기, ③은 한글 직접비교로 교체 — 50·52·53번.)

## 13. 모집단 범위 확정 — 결정 사항

근해/연안을 미리 나누지 않고 **둘 다 넓게 수집 후 태그만 부착**해
score팀이 선택하게 함(원칙1 연장). 모집단 조건은 **EEZ 내 FISHING
이벤트 1건 이상**으로 확정(A/B축이 전부 `fishing.*`에서 나옴). 양식업도
거르지 않고 태그로만 구분. 모집단 자체가 스냅샷 대상임을 명시.
(태깅 기능은 2026-08-18 다운스트림 미사용 확인돼 폐기됨.)

## 14. 4번 단계 마무리 — 남은 미해결 사항

TAC/MR 업종코드 대응, 어선원부 "연계어선번호" 의미, `regions.mpa`
실채움 비율 — 전부 이후 단계(18·22번 등)에서 확인됨.

## 15. 본수집 — 수집 스크립트 구현

`collect/`에 소스별 스크립트 완성(http_common 공통모듈: 재시도·스냅샷·
재개·검증게이트). Events를 먼저 모아 실제 조업 vesselId만 뽑고 그
배들만 상세조회하는 순서로 설계(등록정보 매칭이 거의 없어 Search
선수집이 무의미하므로, 12번 참고). 소량 실호출로 검증 완료. TAC/
어업별어선/어선원부는 API가 막혀있어 정적 파일을 그대로 배치.

실제 발견·수정한 버그 4개: HTTP 201 미처리(status_code==200만 성공
처리하던 것을 `resp.ok` 기준으로 수정), 네트워크 예외 재시도 누락,
Windows 콘솔 유니코드 크래시(UTF-8 강제 reconfigure), **인증키가
메타데이터 URL에 노출되던 것**(원칙4 위반 — 파라미터 직접 구성 후
`serviceKey`를 REDACTED로 치환해 수정).

## 16. 가공 파이프라인 — GFW 이벤트 정규화

`durationHours`(`fishing.averageDurationHours`)가 100% null임을 발견 —
100% 채워진 `start`/`end`로 직접 계산하도록 정규화 로직 변경.

## 17. 가공 파이프라인 — GFW 선박 정규화

`registryInfo`(신뢰도 높음)와 `selfReportedInfo`(낮음)를 접두어로
분리 보존 — 매칭 단계가 출처별 신뢰도를 구분해 쓸 수 있게.

## 18. 매칭 1단계 실행 — TAC ↔ 어선원부 (폐기됨, 52번)

어선번호 정확일치로 1,993척 중 21척(1.1%) 매칭. 일부는 어선번호는
같은데 이름·톤수가 다른 사례 다수 발견 — 어선원부의 "연계어선번호"
필드로 3건은 대체건조(같은 허가슬롯에 배를 새로 지음)임을 확인,
나머지는 원인 불명. **결론(당시)**: 어선원부 값을 "지금 이 배의 정확한
값"으로 확신하면 안 됨 — 이 판단이 이후 52번에서 어선원부를 후보풀에서
아예 빼는 결정의 배경이 됨.

## 19. 매칭 2단계 실행 — GFW ↔ 어선원부 콜사인 (폐기됨, 52번)

콜사인 prefix 매칭을 시도했으나 GFW 콜사인 "306" 하나가 어선원부의
서로 다른 배 6척과 동시에 매칭돼 **폐기** — 정확일치만 신호로 인정하기로
결정(이후 실측 결과 기여분 0.1%/3척뿐이라 52번에서 이 단계 자체를 삭제).

## 20. 매칭 3단계 — 이름 fuzzy 매칭 도입 (2026-08-18 한글 직접비교로 전면 교체됨, 50번)

`korean-romanizer`로 한글명을 로마자화한 뒤 `SequenceMatcher` 유사도로
순위만 매기고 자동 accept/reject는 안 함(옛 TAC 매칭의 7.5~13.2% 정밀도
한계 반복 방지). 표본 10척에서 방법 자체는 작동 확인. 임계값은 미정,
해역신호는 미구현 상태로 다음 단계 진행.

## 21. 매칭 4단계 — 최종 조립 도입

콜사인(고신뢰) > 이름fuzzy(임계값 0.8 이상 중신뢰) > 매칭실패 순 조립.
`FUZZY_NAME_THRESHOLD=0.8`은 표본 10척의 점수 빈 구간을 보고 잡은
잠정값(본수집 후 재조정 필요).

## 22. 근해/연안·양식업 태그 구현 (2026-08-18 다운스트림 미사용으로 폐기됨)

어업별어선(MR) 통계코드 체계(1000=원양~6000=기타)를 그대로 옮겨
업종명 접두어가 아니라 공식 코드로 판정하도록 구현. GFW EEZ12해리
비율 기반 `locationTag`(행동 기준)와 TAC 업종명 기반 `licenseTag`(제도
기준) 2종 부착.

## 23. 해양기상 부착

날짜별 조회 시 지점당 하루 10분단위 시계열이 옴을 확인, 이벤트 시각과
가장 가까운 레코드를 최근접 관측소(Haversine)에서 선택하도록 구현.
공간 정합성 한계(중간값 24.7km, 최대 251km 이격) 발견 —
`weatherStationDistanceKm`을 항상 같이 남겨 후속 단계가 판단하게 함
(거리로 거르지 않음, 원칙1 연장).

## 24. MOF 데이터 매칭 편입 (2026-08-18 후보풀에서 완전 제외됨, 50·52번)

MOF 후보를 그 GFW 선박 전용으로만 추가하도록 확장, 정상 작동 확인.

## 50. 매칭을 로마자 유사도에서 한글 직접비교로 교체(채택) — 최종 재설계

GFW 영문명 4,662척 전체를 사람이 직접 한글로 재변환한 데이터
(`gfw_korean_name_candidates.csv`)가 새로 생기면서, 로마자 변환을
아예 건너뛰는 근본적 해결이 가능해졌다. 로마자 유사도는 서로 다른
이름인데 끝부분이 겹쳐 점수가 높게 나오는 구조적 오탐이 있었음(예:
은성호↔금성호). 사람이 웹 탐색기로 직접 스팟체크하며 여러 버그도
같이 발견·수정(제N호 내부번호 소실, 지오코딩 실패를 후보아님으로
오판, 숫자 하드필터 자릿수 사각지대) — 상세 검증 기록은
`data_new/matching_redesign_proposal/README.md`.

**최종 설계(4단계)**: 한글 exact match만 사용 → 숫자 하드필터(자릿수
무관) → "제N호" 정규화 → 카카오 지오코딩 거리(≤150km) 확인. gearType
보조필터·헝가리안 전역할당도 시도했으나 실익이 작거나(gearType)
오탐률이 높아서(헝가리안 19%) 최종안에서 뺐다. MOF는 이름검색이
어선보다 상선 위주로 편향돼 후보풀에서 아예 뺐다.

**결과**: matched 2,881척(54.1%, 추정 오탐 ~720척) → verified
1,290척(24.2%, 추정 오탐 거의 0) — 오탐 하나가 B축 점수를 배 단위로
완전히 틀어지게 만들 수 있어 커버리지보다 정밀도를 우선(CLAUDE.md
12번). `korean-romanizer` 의존성 제거, 카카오맵 API 의존성 추가.

## 51. verified에서 거리 미확인 singleton 예외 제거 — 예외 없이 단일화

후보가 이름만으로 유일해도 거리를 확인 못 하면(distKm=None) 그냥
통과시키던 조건(`distKm is None or distKm<=150`)을 `distKm is not None
and distKm<=150`으로 단일화 — 거리를 모르면 후보 개수와 무관하게
무조건 보류. **결과**: verified 1,290→**1,262척**(28척은 held_multi로
이동).

## 52. 어선원부를 후보풀에서 완전히 제외 — GFW-TAC 매칭만 사용

어선원부는 2006년 처리배치 일부(전부 비현행)라 TAC 대비 신뢰도가
낮고, 콜사인 경로 기여분도 0.1%(3척)뿐이라 GFW-TAC 단일소스로 정리.
1·2단계 매칭 스크립트, MOF 수집·정규화 스크립트(이미 후보풀에서
빠져 라이브에서 안 읽힘)를 전부 삭제해 파이프라인 단순화. **결과**:
verified 1,262→**1,234척(23.2%)**.

## 53. TAC 쪽 유일성 강제 — verified의 63.8%가 같은 TAC 배 중복배정이었음

발표 방어 논리 점검 중 verified 25쌍 사람 스팟체크로 발견: 서로 다른
GFW 선박 여러 척이 TAC의 같은 배 하나를 동시에 정답으로 주장하는
중복배정이 **verified의 63.8%(787척)**에서 발생(예: TAC "한성호"
1척이 GFW 9척에 매칭) — 숫자 없는 흔한 이름에서 집중 발생, 1~4단계가
GFW 선박마다 독립 판정해서 TAC 쪽 유일성을 전혀 체크 안 했던 게 원인.

**수정**: 5단계 추가 — TAC 등록번호별로 재집계해서 같은 배를 여러
GFW 선박이 주장하면 조업위치 최근접 하나만 verified로 남기고 나머지는
held_multi로 되돌림. **남은 한계**: "최근접"은 확률적 근거지 증명은

**참고**: 옛 로마자 시스템은 TAC+어선원부(최대 3,372개 후보)로
