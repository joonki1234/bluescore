# GFW↔국내등록 선박 매칭 재설계 검토 (2026-08-18, 김태윤)

상태: **팀 결정 대기**. 로마자 유사도 매칭을 한글 직접비교로 바꾸면 정밀도가
얼마나 오르고 대신 뭘 잃는지 정리한 자료. 반영 여부는 팀 결정 필요.

## 배경

현재 라이브에 커밋된 매칭(`data_new/process/assemble_matches.py`,
`FUZZY_NAME_THRESHOLD=0.8`)은 GFW 자기신고 영문명을 로마자로 변환해 국내
등록명(TAC·어선원부)과 문자열 유사도로 비교한다. 사람 라벨링 80쌍 검증에서
**정밀도 약 75%**로 이미 팀 결정에 반영돼 있다(CLAUDE.md 10번).

이번에 GFW 영문명 4,662척 전체를 사람이 직접 한글로 재변환한 데이터
(`gfw_korean_name_candidates.csv`, 3,878척 채워짐, 이미 커밋됨)가
생겨서 — 로마자 대신 한글 원문끼리 직접 비교가 가능해졌다. 그 결과를 검증한
요약이다.

## 발견한 것 3가지

**1. 숫자접두어 필터가 근거는 있는데 코드엔 없음**
PROCESS_LOG 49번에서 "번호 일치 시 정밀도 95~100%, 불일치 시 0%"가
검증됐고 CLAUDE.md가 이 근거로 0.8 임계값을 확정했는데, 정작
`assemble_matches.py`의 `_total_score`엔 반영돼 있지 않다
(nameScore+tonnageBonus+locationBonus뿐, numericBonus 없음).

**2. 로마자 유사도의 구조적 오탐("-성호" 문제)**
서로 다른 실제 이름인데 로마자로 바꾸면 끝부분이 겹쳐서 유사도 점수가
높게 나오는 사례가 실측됨.
```
EUNSEONGHO(실제: 은성호) → 로마자매칭 결과: 금성호(GEUMSEONGHO)로 오매칭
DEOG YANG HO(실제: 덕양호) → 로마자매칭 결과: 동양호로 오매칭(verified 처리됨, nameScore 0.9)
```

**3. 한글 exact-match는 신뢰도 높지만, fuzzy는 위험**
한글 직접비교로 exact match된 벡터는 구조적으로 신뢰도 높음. 반면
fuzzy(0.85+) 허용 시 "제N호"류(선단 일련번호) 이름에서 내부 숫자가 변환
과정에 빠지는 버그로 검증 사례 19건 전부가 오매칭 — fuzzy는 폐기 결정.
```
JE1JOYANGHO  → 제7조양호
JE8JOYANGHO  → 제7조양호   (다른 두 GFW가 같은 배 주장, 최소 하나는 오답)
```

**4. (수정완료) "제N호" 버그가 fuzzy뿐 아니라 exact-only 전체에도 있었음**
old(현재 라이브)/new(이번 시뮬) 5,323척 전체를 교차분석해보니, "old는
확신했는데 new는 못 찾은" 935척 중 124척(13.3%)이 발견 3과 같은 원인
("제707태근호" vs GFW변환 "태근" — 숫자를 통째로 뺀 GFW 쪽과 안 뺀 TAC
원문이 어긋남)이었다. 숫자일치는 이미 별도 하드필터로 확인하니 비교시
"제<숫자>" 접두어를 pool 쪽에서도 떼도 변별력 손실이 없어 — 이미
수정·반영함(`_strip_je_number`). 반영 후 verified 916→1,012, 계산가능
1,451→1,714(27.3%→32.2%)로 늘어남.

**5. (시도했다 폐기) 동률 후보 전역할당 — gearType만 남기고 헝가리안은 뺌**
동률(후보 2개+) 벡터를 하나씩 따로 "제일 가까운 후보"로만 판단하면
서로 다른 GFW벡터가 같은 후보를 동시에 원하는 충돌을 못 알아챈다.
```
GFW '77 HYO CHANG HO'(숫자77) -> 제3효창호(324km) / 제77효창호(268.7km)
GFW '3 HYO CHANG'(숫자3)      -> 제3효창호(355.9km) / 제77효창호(173.0km)
```
독립판단이면 둘 다 제77효창호를 고름(이름상 `3 HYO CHANG`은 명백히
제3효창호인데도). 이걸 풀려고 헝가리안 전역할당까지 시도했으나
**최종 폐기함** — 총비용은 최소화해도 개별 배정의 정답 여부까진
보장 못 해서, 스팟체크로 숫자대조 가능한 37건 중 7건(19%)이
숫자불일치(예: `2 TAE YANG HO`(2)를 `제88태양호`(88)에 배정)로 확인됨.
후보풀에 진짜 정답이 없을 때 억지로 그럴듯한 걸 골라버리는 게 원인 —
19%는 무시 못 할 오탐률이라 폐기.

**gearType 대충매핑(9개 키워드)은 유지** — 개별 최근접 판단으로 이미
풀리는 건 먼저 확정하고, 정말 안 풀리는 것에만 적용. 시행착오로
"gearType 좁혀지면 거리 체크 없이 무조건 verified" 버그도 있었음
(241.9km짜리가 새던 사례 발견) — gearType은 후보를 거르는 용도일 뿐
거리 신뢰도 기준을 대체 못 한다는 원칙 재적용해서 수정.

**6. (수정완료, 제일 큰 정정) 지오코딩 실패가 "유일한 후보"로 둔갑하던 버그**
"이 verified 진짜 확실해?"라는 질문에 표본을 파고들다 발견 — 동률
후보 중 하나만 지오코딩되고 나머지는 실패하면, 그 하나가 "유일하게
가까운 후보"로 확정돼버리고 있었다. 실은 비교 자체가 안 된 것뿐인데.
```
101 CHEONG HAE(숫자101) 후보 4개(전부 이름·숫자 일치):
  대천항(안강망)   -> 지오코딩 실패
  여수시 국동항(잠수기) -> 31.9km 성공  <- 이것만 "유일한 최근접"으로 확정됨
  부산직(REG)      -> 지오코딩 실패("부산직"이 이미 잘린 문자열)
```
TAC 항구명 지오코딩 성공률 66.2%, 어선원부는 18.7%뿐이라(원래도 알던
한계) 이 패턴이 흔했다 — 동률 2,150척 중 336척(15.6%)이 이 버그였음.
"거리 모름"을 "후보 아님"으로 취급한 게 원인 — 후보 전원의 거리를 알
때만 "진짜 유일하게 가깝다"고 판단하도록 수정(`_try_resolve_by_nearest`
가 후보 중 하나라도 거리 미상이면 아예 확정 안 함).

**7. (수정완료) "경쟁자 없는 단독후보"도 거리체크가 아예 없었음 + 카카오 지오코딩으로 전면 교체**
발견 6 수정 직후 배포한 웹 탐색기를 사용자가 직접 훑어보다가 또 잡음:
`2 DEOKSEUNGHO`(숫자2, 1자리라 하드필터 대상 밖)가 `제103덕승호`(201km
거리)에, `315MYEONG CHEON`이 `명천호`(375km)에 **verified**로 확정돼
있었음. 원인은 "후보가 애초에 1개뿐(경쟁자 없음)"인 가장 기본적인
케이스에 거리체크 자체가 없었던 것 — 발견 5·6에서 다른 경로(gearType,
동률타이브레이크)는 다 거리조건을 걸어놨는데 제일 오래된 이 경로만
빠뜨렸다. 같은 거리등급 기준(≤50km verified/50~150km held/초과면
held_multi)을 여기도 적용해 수정.

동시에 지오코딩 자체도 카카오 로컬 API(키워드 장소검색)로 전면 교체함
— 어항113개 큐레이션+시군구centroid 2단계 폴백은 폐기(`geocode_kr.py`
삭제). "대천항"처럼 시군구명 토큰이 없는 항구 고유명사는 그 방식으로
구조적으로 못 찾았는데 카카오는 일반 장소검색이라 대부분 찾음 — TAC
위치 커버리지 66.2%→**96.4%**, 어선원부 18.7%→**94.7%**로 대폭
개선(각각 미해결 72척/73척만 남음, 대부분 원본 데이터가 잘렸거나
너무 작은 동네항구라 지도서비스에도 없는 경우).

**8. (수정완료) 후보 숫자가 1자리라 하드필터를 피해가던 사각지대**
발견 7 반영판을 사용자가 웹 탐색기에서 계속 훑어보다 또 잡음:
`102HAE SANG`(숫자102, 검증된 2~4자리)이 `제8해상호`(숫자8, 1자리라
발견 1의 하드필터엔 안 걸림)에 verified로 확정돼 있었음 — 숫자가
눈으로 보기에도 명백히 다른데 통과된 것. "1자리 숫자는 신호로 안
쓴다"는 원래 설계는 후보생성 하드필터(2~4자리만 비교) 얘기였는데,
이걸 "1자리는 아예 무시"로 확대해석해서 눈에 뻔히 보이는 반대증거까지
못 본 척하고 있었다. 검증된 2~4자리 숫자가 있는데 후보 이름에 다른
숫자가 보이면(1자리 포함) 반대증거로 보고 배제하도록 수정 — 규모는
크지 않지만(18척, ≤50km 기준) 눈에 띄는 오탐이라 바로 잡음.

**최종 반영 후(발견 1~8 전부)**: verified 615척(11.6%), held·위치애매
755척(14.2%), 계산가능 1,370척(25.7%). "골드등급"(숫자 2~4자리
있음+일치+이름일치+거리≤50km 전부 만족) **116척**은 특히 신뢰 높음 —
숫자가 둘 다 2~4자리인데 불일치한 사례, 1자리라도 눈에 보이게
불일치한 사례 둘 다 0건으로 하드필터가 완전히 정상 작동함을 재확인.

## 선택지

**A. 현행 유지** (작업량 없음)
커버리지 54.1% / 정밀도 ~75%(오탐 약 720척 포함 추정). 아무것도 안 바꿈.

**B. 숫자필터만 추가** (작음 — 한 줄 수준)
이미 팀이 인용한 근거(PROCESS_LOG 49번)를 코드에 실제로 반영. 위험 적음,
즉시 가능. 정확한 개선폭은 재실행 후 확인 필요.

**C. 한글비교로 전체 교체** (중간 — 시뮬레이션 코드 포팅)
verified 615척(정밀도 최상) + held 755척(계산 가능, 낮은신뢰도) = 25.7%
커버리지. 스키마 호환이라 B축 소비 코드(`score/real_axis_b_input.py`)는
안 건드려도 됨(`tac`/`mof` 객체 존재 여부만 읽지 `matchTier` 값은 안 봄,
실측 확인함). 단 "0.8 임계값 재론 불필요"로 못박은 팀 결정을 사실상
뒤집는 변경. 카카오맵 API 키가 필요함(`.env`의 `KAKAO_API_KEY`, 개발자
콘솔에서 "카카오맵" 제품 활성화 필요).
